title: Configuration
description: Configure the build with `builder()` in `tsdown.config.ts`, build entries other than `src/module.ts`, and keep packages external.
---

The build is configured in a `tsdown.config.ts` in the module root, with the `builder()` plugin from `@nuxt/module-builder/tsdown`. A module with `src/module.ts` and `src/runtime/` needs no options:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [builder()],
})
```

`tsdown` builds the module with this config, and so does `nuxt-module-build build`. See [Commands](/docs/guide/modules/module-builder/commands). The config is module code, so its relative imports carry their extension, as described in [Module code](/docs/guide/modules/module-builder/typescript#module-code).

## `builder()` options

`builder()` takes three options:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [
    builder({
      entries: [
        './src/utils',
        { input: './src/kit/index', name: 'kit' },
        { input: 'src/features/', outDir: 'dist/features', ext: 'js' },
      ],
      externals: ['shiki'],
      replace: { __VERSION__: JSON.stringify('1.0.0') },
    }),
  ],
})
```

- `entries`: files to build besides `src/module.ts`. An entry is either bundled, like `src/module.ts`, or a directory transpiled file by file, like `src/runtime/`. See [Bundled entries](#bundled-entries) and [Directory entries](#directory-entries).
- `externals`: imports that are never bundled. See [Externals](#externals).
- `replace`: compile-time replacements in the bundled entries, as `{ search: replacement }`, or as `{ values, delimiters, preventAssignment, objectGuards }`.

## Bundled entries

A string, or an object with `input` and an optional `name`, is bundled with tsdown into a single file:

| Option | Description |
|---|---|
| `input` | The entry file, relative to the module root. The extension can be left out. |
| `name` | The output name. Defaults to `input` without `src/` and without its extension. |

Each bundled entry is written to `dist/<name>.mjs`, with its declarations in `dist/<name>.d.mts`. The entries above produce `dist/utils.mjs` and `dist/kit.mjs`. Add each one to the `exports` of `package.json`, as described in [Exports](/docs/guide/modules/module-builder/exports#bundled-entries).

Relative imports in a bundled entry carry the imported file's extension, as in module code, because [source exports](/docs/guide/modules/module-builder/develop-and-publish#source-exports) point at the entry as it is.

## Externals

Bundled entries share the module entry's externals. These are never bundled:

- `@nuxt/kit`, `@nuxt/schema`, `nuxt`, `vue`, and the `#app`, `#build`, and `#imports` aliases.
- Your module's own package name.
- `dependencies`, `peerDependencies`, and `optionalDependencies`.
- The imports in `builder({ externals })`.

Any other import is bundled into the entry that imports it, such as a `devDependency`, or a `#` subpath import from the `imports` field of `package.json`.

To keep a package that isn't a dependency out of the bundled entries, list it in `externals`. Each name also covers its subpaths, so `shiki` keeps `shiki/core` external too. A regular expression matches the import as written. The import is then kept as written, and resolves in the app that installs the module. tsdown's `deps.neverBundle` adds to the same list.

## Directory entries

An object whose `input` ends in `/` is a directory. Every file in it is transpiled on its own, in the same way as `src/runtime/`:

| Option | Description |
|---|---|
| `input` | The source directory, relative to the module root, ending in `/`. |
| `outDir` | The output directory. Defaults to `dist`. It must be inside `dist`. |
| `ext` | The extension of emitted scripts: `mjs` (the default) or `js`. Declarations use the matching `.d.mts` or `.d.ts`. |

The entry above writes the files of `src/features/` to `dist/features/`, with `.js` scripts and `.d.ts` declarations. See [Build output](/docs/guide/modules/module-builder/output#runtime-files) for how each kind of file is emitted.

Files in a directory entry follow the rules of the runtime directory. Their relative imports can leave out the extension, unless module code imports them by value. Module code that imports them points at their output instead of bundling them.

## tsdown options

Other tsdown options apply as usual, such as `outDir` (inside the module), `sourcemap`, `define`, `report`, `plugins`, and `hooks`. `--outDir` and `--sourcemap` on the command line take precedence over the config.

`builder()` sets these options itself, so the build fails when the config sets them too:

- `entry`: list entries in `builder({ entries })` instead.
- `format`, other than `esm`.
- `dts`, other than `true`. Declarations are generated with the module's own tsconfig, see [TypeScript](/docs/guide/modules/module-builder/typescript#declarations).
- `clean`: the output directory is emptied before a one-off build, and a watched build removes the files it no longer emits.
- `unbundle`, `exports`, `fixedExtension: false`, `outExtensions`, `platform` other than `node`, and `workspace`.
- `external` and `noExternal`: use `builder({ externals })`, `deps.neverBundle`, or `deps.alwaysBundle` instead.
- `deps.neverBundle` set to `true` or a function: list the imports instead.

The build also fails when another plugin changes one of these options, or when `outputOptions.entryFileNames` changes the file names of the bundled entries.

### Hooks

`builder()` has no hooks of its own, and fails when it's given `hooks`. Use tsdown's `hooks` in the config, which receive tsdown's context. `ctx.options.cwd` is the module root, and `ctx.options.outDir` the output directory:

- `build:prepare` runs before `builder()` checks the module's imports and empties the output directory, so it can generate sources. Files written into the output directory there are removed.
- `build:done` runs once the build is complete, after `module.json` and `types.d.mts` are written and the paths in `package.json` are checked.

To add a file to the output, emit it from a plugin. It's written before the paths in `package.json` are checked:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  hooks: {
    'build:prepare': ctx => generateTypes(ctx.options.cwd),
  },
  plugins: [
    builder(),
    {
      name: 'config-cjs',
      generateBundle() {
        this.emitFile({ type: 'asset', fileName: 'config.cjs', source: 'module.exports = {}\n' })
      },
    },
  ],
})
```

tsdown's hooks and plugins don't run for `nuxt-module-build prepare`, or for a playground that loads the module from its sources. Commit generated sources that `src/module.ts` imports, or generate them in the module's `dev:prepare` script before `nuxt-module-build prepare`.

### Other builds in the same config

To build other entries alongside the module, export an array of configs. Give each config its own `outDir`, because the module's output directory is emptied before the build. Call `builder()` once, in the config that builds the module:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig([
  { plugins: [builder()] },
  { entry: { cli: 'src/cli.ts' }, outDir: 'dist-cli' },
])
```

## Without a tsdown config

Without a `tsdown.config.ts`, `nuxt-module-build build` builds `src/module.ts` and `src/runtime/` on its own, and reads build options such as `entries` and `externals` from the `build` field of `package.json`:

```json [package.json]
{
  "build": {
    "entries": ["./src/utils"],
    "externals": ["shiki"]
  }
}
```

Entries take the same shapes as in `builder({ entries })`. `tsdown` needs the config to build the module, so a module that builds with `tsdown` moves these options into `builder()`. With a tsdown config, a `build` field fails the build.

## `build.config.ts`

`build.config.ts` (or `.mts`, `.js`, `.mjs`) and the `unbuild` field of `package.json` are deprecated. Without a tsdown config, the build reads them, warns, and still applies these options:

- `entries`, in the shapes described above.
- `externals`: package names and regular expressions.
- `replace` and `rollup.replace`: compile-time replacements in the bundled entries.
- `sourcemap`: `true` emits source maps, like `--sourcemap`.
- The `build:before`, `rollup:done`, and `build:done` hooks.

`mkdist:*` hooks are ignored with a warning, and a few other options are accepted at their defaults. Any other option fails the build, with a list of each one and the file it comes from. With a tsdown config, `build.config.ts` and the `unbuild` field fail the build.

Move their options into `builder()` and tsdown's own `hooks`, then delete the file or remove the field. See [Moving from build.config.ts](/docs/guide/modules/module-builder/upgrade-v2#moving-from-buildconfigts) in the upgrade guide for how each option maps.
