---
title: Configuration
description: Configure the build with `builder()` in `tsdown.config.ts`, build entries other than `src/module.ts`, and keep packages external.
---

You configure the build in a `tsdown.config.ts` in the module root, with the `builder()` plugin from `@nuxt/module-builder/tsdown`. A module with `src/module.ts` and `src/runtime/` needs no options:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [builder()],
})
```

Both `tsdown` and `nuxt-module-build build` build the module with this config. See [Commands](/docs/api/module-builder/commands).

The config is module code, so its relative imports carry their extension. [Module code](/docs/api/module-builder/typescript#module-code) describes the rules.

## `builder()` options

`builder()` takes four options:

| Option | Description |
|---|---|
| `entries` | Files to build besides `src/module.ts`. See [Bundled entries](#bundled-entries) and [Directory entries](#directory-entries). |
| `externals` | Imports that are never bundled. See [Externals](#externals). |
| `replace` | Compile-time replacements in the bundled entries. See [Replacements](#replacements). |
| `declarations` | How declarations are generated. See [Declaration engines](#declaration-engines). |

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [
    builder({
      entries: [
        './src/utils',
        { input: './src/kit/index', name: 'kit' },
        { input: 'src/features/', outDir: 'dist/features', ext: 'js' },
      ],
      externals: ['shiki'],
      replace: { __VERSION__: JSON.stringify('1.0.0') },
    }),
  ],
})
```

## Bundled entries

An entry is either bundled into one file, like `src/module.ts`, or transpiled file by file, like `src/runtime/`. A string, or an object with `input` and an optional `name`, is a bundled entry:

| Option | Description |
|---|---|
| `input` | The entry file, relative to the module root. You can leave out the extension. |
| `name` | The output name. Defaults to `input` without `src/` and without its extension. It can't be `types`, as the build writes `dist/types.d.mts` itself. |

The build writes each bundled entry to `dist/<name>.mjs`, with its declarations in `dist/<name>.d.mts`. The entries in the example above produce `dist/utils.mjs` and `dist/kit.mjs`. Add each one to the `exports` of `package.json`, as described in [Exports](/docs/api/module-builder/exports#bundled-entries).

Relative imports in a bundled entry carry the imported file's extension, as in module code. [Source exports](/docs/api/module-builder/develop-and-publish#source-exports) point at the entry as it is, so the entry has to load as written:

```ts [src/utils.ts]
import { normalizeOptions } from './options.ts'

export function defineMyModuleOptions(options: Record<string, unknown>) {
  return normalizeOptions(options)
}
```

## Directory entries

An object whose `input` ends in `/` is a directory entry. The build transpiles every file in it on its own, in the same way as `src/runtime/`:

| Option | Description |
|---|---|
| `input` | The source directory, relative to the module root, ending in `/`. |
| `outDir` | The output directory. Defaults to `dist`, and must be inside `dist`. |
| `ext` | The extension of emitted scripts: `mjs` (the default) or `js`. Declarations use the matching `.d.mts` or `.d.ts`. |

The entry in the example above writes the files of `src/features/` to `dist/features/`, with `.js` scripts and `.d.ts` declarations. [Build Output](/docs/api/module-builder/output#runtime-files) describes how each kind of file is emitted.

Files in a directory entry follow the rules of the runtime directory. Their relative imports can leave out the extension, unless module code imports them by value. Module code that imports them points at their output, instead of bundling them.

## Externals

Bundled entries share the module entry's externals. The build never bundles these imports:

- `@nuxt/kit`, `@nuxt/schema`, `nuxt`, and `vue`.
- The `#app`, `#build`, and `#imports` aliases.
- Your module's own package name.
- Node builtins, such as `node:fs`.
- The packages in `dependencies`, `peerDependencies`, and `optionalDependencies`.
- The imports in `builder({ externals })` and in tsdown's `deps.neverBundle`.

The build bundles any other import into the entry that imports it, such as a `#` subpath import from the `imports` field of `package.json`. When that bundles a package from `node_modules`, such as a `devDependency`, the build fails with `NUXT_MB_B0004`. For each package that the message names:

- If apps that install the module need the package, move it to `dependencies` or `peerDependencies`.
- If bundling it is intended, list it in tsdown's `deps.onlyBundle`. Set `deps.onlyBundle` to `false` to bundle any package.
- If the app provides it, add it to `externals`.

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  deps: { onlyBundle: ['defu'] },
  plugins: [builder()],
})
```

The check doesn't cover a workspace package that resolves outside `node_modules`. The build bundles it like a file of the module.

To keep a package that isn't a dependency out of the bundled entries, add it to `externals`. A string also covers the package's subpaths, so `shiki` keeps `shiki/core` external too. A regular expression matches the import as written:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [
    builder({
      externals: ['shiki', /^@shikijs\//],
    }),
  ],
})
```

The build keeps an external import as written, and the import resolves in the app that installs the module.

## Replacements

`replace` replaces strings in the bundled entries at build time. Pass an object of search strings and their replacements:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [
    builder({
      replace: { __VERSION__: JSON.stringify('1.0.0') },
    }),
  ],
})
```

To set more options, pass `{ values, delimiters, preventAssignment, objectGuards }` instead. These options follow rolldown's replace plugin.

## Declaration engines

::warning
`declarations.engine` values other than `typescript` are experimental. Their declarations differ from those of TypeScript 6 in how some types are printed.
::

`declarations.engine` selects the compiler that generates the declarations of TypeScript sources: the bundled entries, the declarations of module code that `nuxt-module-build prepare` writes, and the directory entries without `.vue` files. Declarations of `.vue` files always come from `@vue/language-core`, the tooling that `vue-tsc` uses.

| Value | Compiler |
|---|---|
| `typescript` (default) | The module's own TypeScript 5.9 or 6, through its JavaScript API. |
| `typescript7` | TypeScript 7.1 or later, installed next to the module's own, through its native API. It runs in one process for the whole build, and keeps it between rebuilds under `tsdown --watch`. |
| `tsrs` | tsrs, oxc's Rust port of TypeScript 7.1, through the same API. |

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [builder({ declarations: { engine: 'typescript7' } })],
})
```

`nuxt-module-build prepare` reads the option from the same config. Without a tsdown config, or to try an engine without changing the config, set the `NUXT_MODULE_BUILDER_DECLARATION_ENGINE` environment variable to one of the values. It takes precedence over the option for `tsdown`, `nuxt-module-build build` and `nuxt-module-build prepare`.

### Installing an engine

Neither native engine is installed with `@nuxt/module-builder`. The module's own `typescript` stays on 5.9 or 6, which the build and `vue-tsc` need, so install TypeScript 7 next to it under the `@typescript/typescript7` alias, a name that only the TypeScript team can publish:

```bash [Terminal]
# typescript7
pnpm add -D @typescript/typescript7@npm:typescript@beta

# tsrs
pnpm add -D tsrs
```

The build checks that the package it finds is the one it expects, at 7.1 or later, before it runs anything from it. An engine that isn't installed, or is older, fails the build with the command to run.

### Differences from TypeScript 6

TypeScript 7 prints some types differently, so a module's declarations change when it switches engine:

- String literal types keep the quotes of the source: `'md'` instead of `"md"`.
- Union members and object properties can come in another order.
- A default-exported arrow function can be declared as a function: `declare function _default(): void` instead of `declare const _default: () => void`.
- An export destructured from an object can be declared with the same destructuring.

These print the same types another way. A version of TypeScript 7 can print types differently from the previous one, so upgrading it can change the declarations too. `tsrs` prints exactly what the TypeScript 7.1 it ports prints.

TypeScript 7 reports some declaration errors with other codes than TypeScript 6, such as TS2883 instead of TS2742 for an inferred type that can't be named. They fail the build in the same way. See [Declarations](/docs/guide/modules/module-builder/typescript#declarations).

### Platforms and fallback

TypeScript 7 has binaries for every platform that Node supports. The Linux binaries of `tsrs` need glibc 2.34 or later: Debian 12, Ubuntu 22.04 and RHEL 9 or later. Where the selected engine has no binary, or its binary doesn't start, the build generates declarations with the module's own TypeScript and prints one warning, so the same config works for every contributor and in CI.

### Isolated declarations

With `declarations.isolated: true`, oxc generates the declarations of the bundled entries and of the module code that `prepare` writes, from each file on its own. It's faster than a compiler, and works with every `engine`, which still generates the declarations of the directory entries.

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [builder({ declarations: { isolated: true } })],
})
```

Every export of the module code then needs an explicit type, including the module definition, written as `const module: NuxtModule<ModuleOptions> = defineNuxtModule<ModuleOptions>({ ... })` followed by `export default module`. The build fails on each export without one, with its file and position.

The option doesn't change the module's type check: the tsconfig doesn't need `isolatedDeclarations`, so `vue-tsc` doesn't apply its rules. With `declarations.isolated: false`, the selected engine generates these declarations even when the tsconfig sets `isolatedDeclarations`. Without the option, the tsconfig's `isolatedDeclarations` decides.

## tsdown options

Other tsdown options apply as usual, such as `outDir`, `sourcemap`, `define`, `report`, `plugins`, and `hooks`. The output directory must be inside the module. `--outDir` and `--sourcemap` on the command line take precedence over the config:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  outDir: 'build',
  sourcemap: true,
  plugins: [builder()],
})
```

### Options that `builder()` sets

`builder()` sets these options itself, so the build fails when the config sets them too:

- `entry`: list entries in `builder({ entries })` instead.
- `format`, other than `esm`.
- `dts`, other than `true`. Declarations are generated with the module's own tsconfig. See [TypeScript](/docs/api/module-builder/typescript#declarations).
- `clean`: the build empties the output directory before a one-off build. A watched build removes the files that it doesn't emit any more.
- `unbundle`, `exports`, `fixedExtension: false`, `outExtensions`, `platform` other than `node`, and `workspace`.
- `external` and `noExternal`: use `builder({ externals })`, `deps.neverBundle`, or `deps.alwaysBundle` instead.
- `deps.neverBundle` set to `true` or to a function: list the imports instead.

The build also fails when another plugin changes one of these options. It fails when `outputOptions.entryFileNames` changes the file names of the bundled entries, too.

`builder()` also turns off rolldown's `checks.bundlerTimings` report, as most of the plugin time in a module build is declaration generation. Set `checks: { bundlerTimings: true }` in the config to turn it back on.

### Hooks

`builder()` has no hooks of its own, and fails when you pass it `hooks`. Use tsdown's `hooks` in the config instead. They receive tsdown's context, where `ctx.options.cwd` is the module root and `ctx.options.outDir` is the output directory:

- `build:prepare` runs before `builder()` checks the module's imports and empties the output directory. Use it to generate sources. The build removes files that this hook writes into the output directory.
- `build:done` runs once the build is complete. By then, `module.json` and `types.d.mts` are written, and the paths in `package.json` are checked.

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'
import { generateTypes } from './scripts/generate-types.ts'

export default defineConfig({
  hooks: {
    'build:prepare': ctx => generateTypes(ctx.options.cwd),
  },
  plugins: [builder()],
})
```

tsdown's hooks and plugins don't run for `nuxt-module-build prepare`, or for a playground that loads the module from its sources. If `src/module.ts` imports generated sources, commit them. You can also generate them in the module's `dev:prepare` script, before `nuxt-module-build prepare`.

### Extra files in the output

To add a file to the output, emit it from a plugin. The build writes it before it checks the paths in `package.json`:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [
    builder(),
    {
      name: 'config-cjs',
      generateBundle() {
        this.emitFile({ type: 'asset', fileName: 'config.cjs', source: 'module.exports = {}\n' })
      },
    },
  ],
})
```

### Other builds in the same config

To build other entries alongside the module, export an array of configs. Call `builder()` once, in the config that builds the module. Give each config its own `outDir`, because the build empties the module's output directory first:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig([
  { plugins: [builder()] },
  { entry: { cli: 'src/cli.ts' }, outDir: 'dist-cli' },
])
```

## Without a tsdown config

Without a `tsdown.config.ts`, `nuxt-module-build build` builds `src/module.ts` and `src/runtime/` on its own. It reads build options, such as `entries` and `externals`, from the `build` field of `package.json`:

```json [package.json]
{
  "build": {
    "entries": ["./src/utils"],
    "externals": ["shiki"]
  }
}
```

Entries take the same shapes as in `builder({ entries })`.

`tsdown` needs the config to build the module. To build with `tsdown`, move these options into `builder()` and remove the field. With a tsdown config, a `build` field fails the build.

## `build.config.ts`

`build.config.ts` (or `.mts`, `.js`, or `.mjs`) and the `unbuild` field of `package.json` are deprecated. Without a tsdown config, the build reads them, prints a warning, and applies these options:

- `entries`, in the shapes described above.
- `externals`: package names and regular expressions.
- `replace` and `rollup.replace`: compile-time replacements in the bundled entries.
- `sourcemap`: `true` emits source maps, like `--sourcemap`.
- The `build:before`, `rollup:done`, and `build:done` hooks. They receive a context with `options.name`, `options.rootDir`, `options.outDir`, `options.entries`, `options.declaration`, `options.stub` (always `false`), `options.sourcemap`, and `pkg`.

The build ignores `mkdist:*` hooks with a warning, and accepts a few other options at their defaults. Any other option fails the build, with a list of each option and the file that it comes from. With a tsdown config, `build.config.ts` and the `unbuild` field fail the build.

Move their options into `builder()` and tsdown's own `hooks`. Then delete the file, or remove the field. [Move the build options into tsdown.config.ts](/docs/api/module-builder/upgrade-v2#step-2-move-the-build-options-into-tsdownconfigts) in the upgrade guide shows how each option maps.
