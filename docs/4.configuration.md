title: Configuration
description: Configure the build with `builder()` in `tsdown.config.ts`, build entries other than `src/module.ts`, and keep packages external.
---

You configure the build in a `tsdown.config.ts` in the module root, with the `builder()` plugin from `@nuxt/module-builder/tsdown`. A module with `src/module.ts` and `src/runtime/` needs no options:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [builder()],
})
```

Both `tsdown` and `nuxt-module-build build` build the module with this config. See [Commands](/docs/guide/modules/module-builder/commands).

The config is module code, so its relative imports carry their extension. [Module code](/docs/guide/modules/module-builder/typescript#module-code) describes the rules.

## `builder()` options

`builder()` takes three options:

| Option | Description |
|---|---|
| `entries` | Files to build besides `src/module.ts`. See [Bundled entries](#bundled-entries) and [Directory entries](#directory-entries). |
| `externals` | Imports that are never bundled. See [Externals](#externals). |
| `replace` | Compile-time replacements in the bundled entries. See [Replacements](#replacements). |

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [
    builder({
      entries: [
        './src/utils',
        { input: './src/kit/index', name: 'kit' },
        { input: 'src/features/', outDir: 'dist/features', ext: 'js' },
      ],
      externals: ['shiki'],
      replace: { __VERSION__: JSON.stringify('1.0.0') },
    }),
  ],
})
```

## Bundled entries

An entry is either bundled into one file, like `src/module.ts`, or transpiled file by file, like `src/runtime/`. A string, or an object with `input` and an optional `name`, is a bundled entry:

| Option | Description |
|---|---|
| `input` | The entry file, relative to the module root. You can leave out the extension. |
| `name` | The output name. Defaults to `input` without `src/` and without its extension. It can't be `types`, as the build writes `dist/types.d.mts` itself. |

The build writes each bundled entry to `dist/<name>.mjs`, with its declarations in `dist/<name>.d.mts`. The entries in the example above produce `dist/utils.mjs` and `dist/kit.mjs`. Add each one to the `exports` of `package.json`, as described in [Exports](/docs/guide/modules/module-builder/exports#bundled-entries).

Relative imports in a bundled entry carry the imported file's extension, as in module code. [Source exports](/docs/guide/modules/module-builder/develop-and-publish#source-exports) point at the entry as it is, so the entry has to load as written:

```ts [src/utils.ts]
import { normalizeOptions } from './options.ts'

export function defineMyModuleOptions(options: Record<string, unknown>) {
  return normalizeOptions(options)
}
```

## Directory entries

An object whose `input` ends in `/` is a directory entry. The build transpiles every file in it on its own, in the same way as `src/runtime/`:

| Option | Description |
|---|---|
| `input` | The source directory, relative to the module root, ending in `/`. |
| `outDir` | The output directory. Defaults to `dist`, and must be inside `dist`. |
| `ext` | The extension of emitted scripts: `mjs` (the default) or `js`. Declarations use the matching `.d.mts` or `.d.ts`. |

The entry in the example above writes the files of `src/features/` to `dist/features/`, with `.js` scripts and `.d.ts` declarations. [Build Output](/docs/guide/modules/module-builder/output#runtime-files) describes how each kind of file is emitted.

Files in a directory entry follow the rules of the runtime directory. Their relative imports can leave out the extension, unless module code imports them by value. Module code that imports them points at their output, instead of bundling them.

## Externals

Bundled entries share the module entry's externals. The build never bundles these imports:

- `@nuxt/kit`, `@nuxt/schema`, `nuxt`, and `vue`.
- The `#app`, `#build`, and `#imports` aliases.
- Your module's own package name.
- The packages in `dependencies`, `peerDependencies`, and `optionalDependencies`.
- The imports in `builder({ externals })` and in tsdown's `deps.neverBundle`.

The build bundles any other import into the entry that imports it. That includes a `devDependency`, and a `#` subpath import from the `imports` field of `package.json`.

To keep a package that isn't a dependency out of the bundled entries, add it to `externals`. A string also covers the package's subpaths, so `shiki` keeps `shiki/core` external too. A regular expression matches the import as written:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [
    builder({
      externals: ['shiki', /^@shikijs\//],
    }),
  ],
})
```

The build keeps an external import as written, and the import resolves in the app that installs the module.

## Replacements

`replace` replaces strings in the bundled entries at build time. Pass an object of search strings and their replacements:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [
    builder({
      replace: { __VERSION__: JSON.stringify('1.0.0') },
    }),
  ],
})
```

To set more options, pass `{ values, delimiters, preventAssignment, objectGuards }` instead. These options follow rolldown's replace plugin.

## tsdown options

Other tsdown options apply as usual, such as `outDir`, `sourcemap`, `define`, `report`, `plugins`, and `hooks`. The output directory must be inside the module. `--outDir` and `--sourcemap` on the command line take precedence over the config:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  outDir: 'build',
  sourcemap: true,
  plugins: [builder()],
})
```

### Options that `builder()` sets

`builder()` sets these options itself, so the build fails when the config sets them too:

- `entry`: list entries in `builder({ entries })` instead.
- `format`, other than `esm`.
- `dts`, other than `true`. Declarations are generated with the module's own tsconfig. See [TypeScript](/docs/guide/modules/module-builder/typescript#declarations).
- `clean`: the build empties the output directory before a one-off build. A watched build removes the files that it doesn't emit any more.
- `unbundle`, `exports`, `fixedExtension: false`, `outExtensions`, `platform` other than `node`, and `workspace`.
- `external` and `noExternal`: use `builder({ externals })`, `deps.neverBundle`, or `deps.alwaysBundle` instead.
- `deps.neverBundle` set to `true` or to a function: list the imports instead.

The build also fails when another plugin changes one of these options. It fails when `outputOptions.entryFileNames` changes the file names of the bundled entries, too.

`builder()` also turns off rolldown's `checks.bundlerTimings` report, as most of the plugin time in a module build is declaration generation. Set `checks: { bundlerTimings: true }` in the config to turn it back on.

### Hooks

`builder()` has no hooks of its own, and fails when you pass it `hooks`. Use tsdown's `hooks` in the config instead. They receive tsdown's context, where `ctx.options.cwd` is the module root and `ctx.options.outDir` is the output directory:

- `build:prepare` runs before `builder()` checks the module's imports and empties the output directory. Use it to generate sources. The build removes files that this hook writes into the output directory.
- `build:done` runs once the build is complete. By then, `module.json` and `types.d.mts` are written, and the paths in `package.json` are checked.

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'
import { generateTypes } from './scripts/generate-types.ts'

export default defineConfig({
  hooks: {
    'build:prepare': ctx => generateTypes(ctx.options.cwd),
  },
  plugins: [builder()],
})
```

tsdown's hooks and plugins don't run for `nuxt-module-build prepare`, or for a playground that loads the module from its sources. If `src/module.ts` imports generated sources, commit them. You can also generate them in the module's `dev:prepare` script, before `nuxt-module-build prepare`.

### Extra files in the output

To add a file to the output, emit it from a plugin. The build writes it before it checks the paths in `package.json`:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig({
  plugins: [
    builder(),
    {
      name: 'config-cjs',
      generateBundle() {
        this.emitFile({ type: 'asset', fileName: 'config.cjs', source: 'module.exports = {}\n' })
      },
    },
  ],
})
```

### Other builds in the same config

To build other entries alongside the module, export an array of configs. Call `builder()` once, in the config that builds the module. Give each config its own `outDir`, because the build empties the module's output directory first:

```ts [tsdown.config.ts]
import { builder } from '@nuxt/module-builder/tsdown'
import { defineConfig } from 'tsdown'

export default defineConfig([
  { plugins: [builder()] },
  { entry: { cli: 'src/cli.ts' }, outDir: 'dist-cli' },
])
```

## Without a tsdown config

Without a `tsdown.config.ts`, `nuxt-module-build build` builds `src/module.ts` and `src/runtime/` on its own. It reads build options, such as `entries` and `externals`, from the `build` field of `package.json`:

```json [package.json]
{
  "build": {
    "entries": ["./src/utils"],
    "externals": ["shiki"]
  }
}
```

Entries take the same shapes as in `builder({ entries })`.

`tsdown` needs the config to build the module. To build with `tsdown`, move these options into `builder()` and remove the field. With a tsdown config, a `build` field fails the build.

## `build.config.ts`

`build.config.ts` (or `.mts`, `.js`, or `.mjs`) and the `unbuild` field of `package.json` are deprecated. Without a tsdown config, the build reads them, prints a warning, and applies these options:

- `entries`, in the shapes described above.
- `externals`: package names and regular expressions.
- `replace` and `rollup.replace`: compile-time replacements in the bundled entries.
- `sourcemap`: `true` emits source maps, like `--sourcemap`.
- The `build:before`, `rollup:done`, and `build:done` hooks. They receive a context with `options.name`, `options.rootDir`, `options.outDir`, `options.entries`, `options.declaration`, `options.stub` (always `false`), `options.sourcemap`, and `pkg`.

The build ignores `mkdist:*` hooks with a warning, and accepts a few other options at their defaults. Any other option fails the build, with a list of each option and the file that it comes from. With a tsdown config, `build.config.ts` and the `unbuild` field fail the build.

Move their options into `builder()` and tsdown's own `hooks`. Then delete the file, or remove the field. [Moving from build.config.ts](/docs/guide/modules/module-builder/upgrade-v2#moving-from-buildconfigts) in the upgrade guide shows how each option maps.
