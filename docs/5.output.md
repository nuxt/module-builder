---
title: Build Output
description: The files that `nuxt-module-build build` writes to `dist`.
---

A module with `src/module.ts`, `src/runtime/`, and a `./src/utils` [entry](/docs/guide/modules/module-builder/configuration#bundled-entries) builds into:

```bash
dist/
├── module.mjs       # src/module.ts, bundled
├── module.d.mts     # its declarations
├── module.json      # the module's meta
├── types.d.mts      # the types that `exports["."].types` points at
├── utils.mjs        # src/utils.ts, bundled
├── utils.d.mts
└── runtime/         # src/runtime/, file by file
```

The output is ES modules only. Pass `--sourcemap` to emit a source map next to every script.

## `module.mjs`

`src/module.ts`, bundled with tsdown. It's compiled for the lowest Node version in your module's `engines.node` field. Without that field, its syntax is kept as written.

Imports of the runtime directory, and of other directory entries, point at their output in `dist` and aren't bundled. See [Configuration](/docs/guide/modules/module-builder/configuration#bundled-entries) for the packages that stay external.

## `module.json`

The module's meta. It contains the `meta` of the module definition, and the versions of `@nuxt/module-builder` and `tsdown` that built it. When the definition doesn't set `name` or `version`, they come from `package.json`. The build loads `dist/module.mjs` to read it.

```json [dist/module.json]
{
  "name": "my-module",
  "configKey": "myModule",
  "version": "1.0.0",
  "builder": {
    "@nuxt/module-builder": "2.0.0",
    "tsdown": "0.23.7"
  }
}
```

## `types.d.mts`

The types of the package's root export. It re-exports everything `module.d.mts` exports, and adds the [type exports](/docs/guide/modules/module-builder/project-structure#srcmodulets) of `src/module.ts` to Nuxt's own types:

```ts [dist/types.d.mts]
import type { ModuleHooks, ModuleRuntimeHooks, ModuleRuntimeConfig, ModulePublicRuntimeConfig } from './module.mjs'

declare module '#app' {
  interface RuntimeNuxtHooks extends ModuleRuntimeHooks {}
}

declare module '@nuxt/schema' {
  interface NuxtHooks extends ModuleHooks {}
  interface RuntimeConfig extends ModuleRuntimeConfig {}
  interface PublicRuntimeConfig extends ModulePublicRuntimeConfig {}
}

export { type ModuleHooks, type ModuleOptions, type ModulePublicRuntimeConfig, type ModuleRuntimeConfig, type ModuleRuntimeHooks, default } from './module.mjs'
```

When `src/module.ts` doesn't export `ModuleOptions`, `types.d.mts` infers it from the default export.

## Runtime files

Every file under `src/runtime/` is emitted under `dist/runtime/` with its name intact, apart from the extension:

| Source | Output |
|---|---|
| Scripts: `.ts`, `.mts`, `.cts`, `.js`, `.mjs`, `.cjs` | `.js`, with a `.d.ts` declaration |
| `.tsx`, `.jsx` | `.jsx`, with types stripped and the JSX kept, and a `.d.ts` declaration. See [JSX](#jsx). |
| `.vue` | `.vue`, with TypeScript stripped, and `.d.vue.ts` and `.vue.d.ts` declarations |
| `.css` | `.css`, with nesting flattened, vendor prefixes added for the project's browserslist targets, and minified |
| `.scss`, `.sass` | `.css`, compiled with your module's `sass` or `sass-embedded`. Partials (`_name.scss`) aren't emitted. |
| Anything else, including `.d.ts` | Copied as it is |

Test and story files (`*.spec.ts`, `*.test.ts`, `*.stories.ts`, and their other script extensions) are left out.

Scripts are transpiled with oxc, one file at a time. Each keeps its own imports and exports:

- Relative imports get the emitted extension: `../utils/merge` becomes `../utils/merge.js`, and `./styles.scss` becomes `./styles.css`.
- Non-relative imports (`#imports`, `#build/*`, and packages) are kept as written.
- Imports used only as types are removed.

A relative import of a file outside `src/runtime/` emits that file too, where the import points: `src/shared/x.ts` becomes `dist/shared/x.js`. When that would leave `dist` or take the name of another output, it's emitted under `dist/_external/` instead. A file that is only imported for its types gets a declaration and no script.

`.css` `@import` statements are kept as written. Postcss configuration isn't applied to runtime stylesheets; process them in the Nuxt app, or before the build.

Other [directory entries](/docs/guide/modules/module-builder/configuration#directory-entries) are emitted in the same way, under their own `outDir`, with `.mjs` and `.d.mts` unless their `ext` is `js`. In every directory, a file whose JSX is kept is emitted as `.jsx` with a `.d.ts`.

### JSX

`.tsx` and `.jsx` files keep their JSX, so the app that installs the module compiles it with its own Vue JSX plugin. Refer to these files without an extension, as in `resolver.resolve('./runtime/components/Banner')`. The path then resolves to the `.tsx` source in development and to the `.jsx` output once the module is published.

Nitro and Node don't transform files in `node_modules`. JSX that runs there is compiled to `vue/jsx-runtime` calls instead, and the file is emitted as `.js`. This applies to:

- Scripts under a `server/` directory.
- Runtime files that these scripts or a bundled entry, such as `src/module.ts`, import values from through relative paths.

An import through an alias or through the module's own package name isn't followed.

## Runtime declarations

Declarations of runtime files are rewritten so they resolve in the app that installs the module:

- Relative imports get the extension of the file they resolve to, for `node16` and `nodenext` module resolution.
- `#app` imports become `nuxt/app`.
- Other Nuxt aliases, such as `#build/*` and `#imports`, are kept. They resolve against the `.nuxt` of the app that installs the module.

See [TypeScript](/docs/guide/modules/module-builder/typescript#declarations) for how declarations are generated, and the errors that fail the build.
