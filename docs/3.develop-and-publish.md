A module has a script for each stage of its life: preparing a fresh checkout, running the playground, and publishing a release. This page describes what each one does. To create a module from the starter, see [Getting Started](/docs/guide/modules/module-builder). To move a module that used stub builds, see [Stub builds](/docs/guide/modules/module-builder/upgrade-v2#stub-builds) in the upgrade guide.

## Preparing a checkout

The [playground](/docs/guide/modules/module-builder/project-structure#playground) installs the module by its package name, so it loads whatever `package.json` points at. Which setup to use depends on the package manager that publishes the module:

- With pnpm or Yarn 4, `package.json` points at your sources, and `publishConfig` holds the `dist` paths that are published. The playground runs your sources, and `dist` is only written when you build. See [Source exports](#source-exports).
- With npm, Yarn 3 or earlier, or bun, `package.json` points at `dist`, and `tsdown --watch` rebuilds it while you develop. See [Developing against `dist`](#developing-against-dist).

Run `dev:prepare` after you install dependencies, and again when the types it generates are out of date, such as after the module registers a new template or server route. The build runs `prepare` on its own when `.nuxt` is missing. Keeping `prepare` in `dev:prepare` puts the module's types in place before your editor or type check needs them.

### Source exports

pnpm and Yarn 4 publish the fields of `publishConfig` in place of the top-level ones. With either of them, point `exports` and `main` at `src`, and the same fields in `publishConfig` at `dist`:

```json [package.json]
{
  "exports": {
    ".": {
      "types": "./.nuxt/module-builder/types.d.mts",
      "import": "./src/module.ts"
    }
  },
  "main": "./src/module.ts",
  "files": [
    "dist"
  ],
  "publishConfig": {
    "exports": {
      ".": {
        "types": "./dist/types.d.mts",
        "import": "./dist/module.mjs"
      }
    },
    "main": "./dist/module.mjs"
  },
  "scripts": {
    "dev": "nuxt dev playground",
    "dev:prepare": "nuxt-module-build prepare && nuxt prepare playground",
    "prepack": "tsdown"
  }
}
```

1. `nuxt-module-build prepare` generates the module's own `.nuxt`, for the module's `tsconfig.json`, and the `.nuxt/module-builder/types.d.mts` that the root export's `types` condition points at. See [`prepare`](/docs/guide/modules/module-builder/commands#prepare).
2. `nuxt prepare playground` generates the playground's `.nuxt`. It loads `src/module.ts` through `exports`.

`publishConfig` replaces each field as a whole, so `publishConfig.exports` repeats every subpath and condition of `exports`. See [Exports](/docs/guide/modules/module-builder/exports#source-exports) for subpaths.

The playground has to resolve the module's name to the module directory itself. With pnpm, install it with `workspace:*` and list `playground` in `pnpm-workspace.yaml`, or with `link:..`:

```yaml [pnpm-workspace.yaml]
packages:
  - playground
```

```json [playground/package.json]
{
  "dependencies": {
    "my-module": "workspace:*"
  }
}
```

The playground's type check includes your sources and the files they import types from. See [The playground's `tsconfig.json`](/docs/guide/modules/module-builder/typescript#with-source-exports) for the errors this can report.

There is no `dist` while you develop, so code that reaches into `dist` by path points at `src` instead. Resolve runtime files relative to `src/module.ts` and without an extension, as in `createResolver(import.meta.url).resolve('./runtime/app/plugins/greeting')`. The build keeps the layout of `src` in `dist`, and Nuxt adds the extension.

Build-time code that reads a runtime file's contents, such as code that inlines the file into a template, finds no file at the path without an extension, and TypeScript at the `.ts` path. Generate the template from code that doesn't depend on the built file, or build `dist` first and keep reading from it.

Yarn 4 packs `typesVersions` as written. Keep `typesVersions` at the top level, pointing at `dist`: TypeScript only reads it under `node10` module resolution, which a playground doesn't use.

### Developing against `dist`

npm, Yarn 3 and earlier, and bun publish some or all of these fields as written. With them, point `package.json` at `dist`, and build it before the playground is prepared:

```json [package.json]
{
  "exports": {
    ".": {
      "types": "./dist/types.d.mts",
      "import": "./dist/module.mjs"
    }
  },
  "main": "./dist/module.mjs",
  "files": [
    "dist"
  ],
  "scripts": {
    "dev": "nuxt dev playground",
    "dev:prepare": "nuxt-module-build prepare && tsdown && nuxt prepare playground",
    "prepack": "tsdown"
  }
}
```

1. `nuxt-module-build prepare` generates the module's own `.nuxt`, for the module's `tsconfig.json`.
2. `tsdown` builds `dist`. See [`tsdown`](/docs/guide/modules/module-builder/commands#tsdown).
3. `nuxt prepare playground` generates the playground's `.nuxt`. It loads `dist/module.mjs` through `exports`.

With npm, install the module in the playground with `"my-module": "file:.."` and list `playground` in the root `workspaces`, so npm links the module into the playground. With Yarn 1, use `"my-module": "link:.."`.

`nuxt-module-build prepare` installs the module from its sources even where its own `.nuxtrc` or `nuxt.config` lists it by name. Any other `nuxt prepare` that loads the module by name, such as one at the repository root with `modules[]=my-module` in `.nuxtrc`, loads it from `dist` and leaves it out when `dist` is missing. Run `tsdown` before such a `nuxt prepare` in `dev:prepare`.

While the playground runs, run `tsdown --watch` next to it. It leaves `dist` in place while its first build runs, so the two can start together. Each change under `src` rebuilds `dist`, and a rebuild only writes the files whose content changed.

## Working in the playground

The playground is a Nuxt app that installs your module, so you can try it out as you change it:

- `npm run dev` starts the playground's development server with `nuxt dev playground`.
- `npm run dev:build` builds the playground with `nuxt build playground`.
- Any other `nuxt` command works against the playground too, as `nuxt <command> playground`.

Nuxt serves the files of the runtime directory through Vite, so an edited component updates in place, and an edited plugin reloads the page. With `dist`, this applies once `tsdown --watch` has rebuilt the file. The playground loads the module itself once, when `nuxt dev` starts: restart `nuxt dev` after you change `src/module.ts` or the files it imports.

With source exports, the playground always runs your sources. With `package.json` pointing at `dist`, it runs the last build. To try the output of a full build there, build the module and start the playground:

```bash
npx tsdown && npx nuxt dev playground
```

See [Testing](/docs/guide/modules/testing) in the Module Author Guide for the tests themselves.

## Publishing

The `prepack` script runs `tsdown`, so the package manager builds the module whenever it packs or publishes it. You don't need to build it yourself first.

Before your first release, create an account on [npmjs.com](https://www.npmjs.com) and log in with `npm login`. To check the package before you publish it, pack the module with the package manager that publishes it, such as `pnpm pack` for source exports. Then run [publint](https://publint.dev) and [Are the Types Wrong?](https://arethetypeswrong.github.io) on the tarball:

```bash
pnpm pack
npx publint ./my-module-1.0.0.tgz
npx @arethetypeswrong/cli ./my-module-1.0.0.tgz
```

A `release` script can publish a new version in one step:

```json [package.json]
{
  "scripts": {
    "release": "pnpm lint && pnpm test && pnpm prepack && changelogen --release && pnpm publish && git push --follow-tags"
  }
}
```

1. It runs the linter, the tests, and the build. The release stops if any of them fails.
2. `changelogen --release` bumps the version, updates `CHANGELOG.md` from your commit messages, and commits and tags the result.
3. `pnpm publish` publishes the package. `prepack` builds the module again, so `dist` has the new version.
4. `git push --follow-tags` pushes the release commit and its tag.

With source exports, publish with `pnpm publish` or `yarn npm publish`. With `dist`, `npm publish` works too.

Commit your changes before you run `release`. `changelogen` reads [Conventional Commits](https://www.conventionalcommits.org) to choose the version bump and to write the changelog.

### Checks on published paths

Every build reads the path fields of `package.json`, such as `exports`, `main`, and `types`, with the fields of `publishConfig` in place of the top-level ones. It fails before building when one of them points at a path that doesn't work once the package is installed:

- A TypeScript source other than a declaration, which Node doesn't load from `node_modules`.
- A path that the pack leaves out, because `files` doesn't list it. Without `files`, a path into `.nuxt` counts as left out.

Every pack includes `package.json` and the file that `main` points at, so `files` doesn't have to list them. To publish a file other than a TypeScript source as it is, list it in `files`.

An entry of `imports` is checked in the same way once the build is done, and only when the build output imports it. An entry that the build bundles into `module.mjs` can keep pointing at `src`.

When `tsdown` or `nuxt-module-build build` runs as the `prepack` or `prepublishOnly` script, the build also fails when the package manager that packs would publish such a path as written:

- The package manager has to apply `publishConfig` to each field that points at your sources. pnpm applies it to all of them. Yarn 4 applies it to every field but `typesVersions`, Yarn 3 to `exports`, `imports`, `main`, and `module`, and Yarn 2 to `main` and `module`. npm, Yarn 1, and bun pack `package.json` as written.
- `publishConfig` has to set each of those fields, to paths that pass the checks above.

The build reads the package manager from the `npm_config_user_agent` and `npm_execpath` environment variables, and the script from `npm_lifecycle_event`. A `prepack` script that runs another script, such as `"prepack": "npm run build"`, isn't checked, because the nested script runs as `build`. Run `tsdown` or `nuxt-module-build build` from `prepack` directly. With source exports, a `release` script that runs `npm publish` fails, even when `pnpm run` starts it. `npm publish` of a tarball that `pnpm pack` wrote works, as its `package.json` already has the `dist` paths and the build doesn't run again.

After the build, a warning lists the paths in `package.json` that the build didn't produce.
