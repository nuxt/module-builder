A module has a script for each stage of its life: preparing a fresh checkout, running the playground, and publishing a release. This page describes what each script does, and the two development setups that they depend on.

To create a module from the starter, see [Getting Started](/docs/guide/modules/module-builder). To move a module that used stub builds in v1, see [Stub builds](/docs/guide/modules/module-builder/upgrade-v2#stub-builds) in the upgrade guide.

## Preparing a checkout

The [playground](/docs/guide/modules/module-builder/project-structure#playground) installs the module by its package name, so it loads whatever `package.json` points at. The package manager that publishes your module decides which setup you use:

| Package manager | `package.json` points at | While you develop |
|---|---|---|
| pnpm, Yarn 4 | Your sources, with the `dist` paths in `publishConfig` | The playground runs your sources. See [Source exports](#source-exports). |
| npm, Yarn 3 and earlier, bun | `dist` | `tsdown --watch` rebuilds `dist`. See [Developing against `dist`](#developing-against-dist). |

A playground that lists the module by relative path, as `modules: ['../src/module']`, loads `src/module.ts` in both setups, and its type check doesn't see the module's [type augmentations](/docs/guide/modules/module-builder/project-structure#srcmodulets). See [`playground/`](/docs/guide/modules/module-builder/project-structure#playground).

Run `dev:prepare` after you install dependencies. Run it again when the types that it generates are out of date, such as after the module registers a new template or server route. The module's own app, server and shared type checks see the types of module code as of the last `prepare`.

The build runs `prepare` on its own when `.nuxt` is missing. Keep `prepare` in `dev:prepare` anyway, so the module's types are in place before your editor or your type check needs them.

### Source exports

pnpm and Yarn 4 publish the fields of `publishConfig` in place of the top-level ones. With either of them, point `exports` and `main` at `src`, and the same fields in `publishConfig` at `dist`:

```json [package.json]
{
  "exports": {
    ".": {
      "types": "./.nuxt/module-builder/types.d.mts",
      "import": "./src/module.ts"
    }
  },
  "main": "./src/module.ts",
  "files": [
    "dist"
  ],
  "publishConfig": {
    "exports": {
      ".": {
        "types": "./dist/types.d.mts",
        "import": "./dist/module.mjs"
      }
    },
    "main": "./dist/module.mjs"
  },
  "scripts": {
    "dev": "nuxt dev playground",
    "dev:prepare": "nuxt-module-build prepare && nuxt prepare playground",
    "prepack": "tsdown"
  }
}
```

`dev:prepare` runs two commands:

1. `nuxt-module-build prepare` generates the module's own `.nuxt`, for the module's `tsconfig.json`. It also writes the `.nuxt/module-builder/types.d.mts` that the root export's `types` condition points at. See [`prepare`](/docs/guide/modules/module-builder/commands#prepare).
2. `nuxt prepare playground` generates the playground's `.nuxt`. It loads `src/module.ts` through `exports`.

`publishConfig` replaces each field as a whole, so `publishConfig.exports` repeats every subpath and condition of `exports`. [Exports](/docs/guide/modules/module-builder/exports#source-exports) shows an example with subpaths.

The playground has to resolve the module's name to the module directory itself. With pnpm, list `playground` in `pnpm-workspace.yaml`, and install the module with `workspace:*` or `link:..`:

```yaml [pnpm-workspace.yaml]
packages:
  - playground
```

```json [playground/package.json]
{
  "dependencies": {
    "my-module": "workspace:*"
  }
}
```

The playground's type check includes your sources and the files that they import types from. [The playground's `tsconfig.json`](/docs/guide/modules/module-builder/typescript#with-source-exports) lists the errors that this can report.

Yarn 4 packs `typesVersions` as written. Keep `typesVersions` at the top level, pointing at `dist`. TypeScript only reads it under `node10` module resolution, which a playground doesn't use.

#### Code that reaches into `dist`

There is no `dist` while you develop, so code that reaches into `dist` by path has to point at `src`. Resolve runtime files relative to `src/module.ts`, without an extension:

```ts [src/module.ts]
import { addPlugin, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module', configKey: 'myModule' },
  setup() {
    const resolver = createResolver(import.meta.url)

    addPlugin(resolver.resolve('./runtime/app/plugins/greeting'))
  },
})
```

The build keeps the layout of `src` in `dist`, and Nuxt adds the extension.

Build-time code that reads a runtime file's contents, such as code that inlines the file into a template, needs more care. It finds no file at the path without an extension, and TypeScript at the `.ts` path. Generate the template from code that doesn't depend on the built file:

```ts [src/module.ts]
import { addTemplate, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module', configKey: 'myModule' },
  defaults: { languages: ['ts', 'vue'] },
  setup(options) {
    addTemplate({
      filename: 'my-module/languages.mjs',
      getContents: () => `export const languages = ${JSON.stringify(options.languages)}`,
    })
  },
})
```

If the template has to contain the built file, build `dist` first and keep reading from `dist`.

### Developing against `dist`

npm, Yarn 3 and earlier, and bun publish some or all of these fields as written. With them, point `package.json` at `dist`, and build `dist` before the playground is prepared:

```json [package.json]
{
  "exports": {
    ".": {
      "types": "./dist/types.d.mts",
      "import": "./dist/module.mjs"
    }
  },
  "main": "./dist/module.mjs",
  "files": [
    "dist"
  ],
  "scripts": {
    "dev": "nuxt dev playground",
    "dev:prepare": "nuxt-module-build prepare && tsdown && nuxt prepare playground",
    "prepack": "tsdown"
  }
}
```

`dev:prepare` runs three commands:

1. `nuxt-module-build prepare` generates the module's own `.nuxt`, for the module's `tsconfig.json`.
2. `tsdown` builds `dist`. See [`tsdown`](/docs/guide/modules/module-builder/commands#tsdown).
3. `nuxt prepare playground` generates the playground's `.nuxt`. It loads `dist/module.mjs` through `exports`.

With npm, list `playground` in the root `workspaces`, and install the module in the playground with `"my-module": "file:.."`. npm then links the module into the playground. With Yarn 1, use `"my-module": "link:.."`.

While the playground runs, run `tsdown --watch` next to it:

```bash [Terminal]
npx tsdown --watch
```

Watch mode keeps `dist` in place while its first build runs, so you can start both at the same time. Each change under `src` rebuilds `dist`, and a rebuild only writes the files whose content changed.

#### Other `nuxt prepare` commands

`nuxt-module-build prepare` installs the module from its sources, even where the module's own `.nuxtrc` or `nuxt.config` lists it by name. Any other `nuxt prepare` that loads the module by name loads it from `dist`, and leaves the module out when `dist` is missing. One example is a `nuxt prepare` at the repository root, with `modules[]=my-module` in its `.nuxtrc`. Run `tsdown` before such a command:

```json [package.json]
{
  "scripts": {
    "dev:prepare": "nuxt-module-build prepare && tsdown && nuxt prepare && nuxt prepare playground"
  }
}
```

## Working in the playground

The playground is a Nuxt app that installs your module, so you can try the module as you change it:

- `npm run dev` starts the playground's development server with `nuxt dev playground`.
- `nuxt build playground` builds the playground.
- Any other `nuxt` command works against the playground too, as `nuxt <command> playground`.

Nuxt serves the files of the runtime directory through Vite. An edited component updates in place, and an edited plugin reloads the page. When the playground runs `dist`, this happens after `tsdown --watch` rebuilds the file.

The playground loads the module itself once, when `nuxt dev` starts. Restart `nuxt dev` after you change `src/module.ts` or the files that it imports.

With source exports, the playground always runs your sources. When `package.json` points at `dist`, the playground runs the last build. To try a full build there, build the module and start the playground:

```bash [Terminal]
npx tsdown && npx nuxt dev playground
```

For the module's tests, see [Testing](/docs/guide/modules/testing) in the Module Author Guide.

## Publishing

The `prepack` script runs `tsdown`, so the package manager builds the module whenever it packs or publishes it. You don't need to build the module yourself first.

Before your first release, create an account on [npmjs.com](https://www.npmjs.com) and log in with `npm login`.

### Checking the package

To check the package before you publish it, follow these steps:

1. Pack the module with the package manager that publishes it, such as `pnpm pack` for source exports:

   ```bash [Terminal]
   pnpm pack
   ```

2. Run [publint](https://publint.dev) on the tarball:

   ```bash [Terminal]
   npx publint ./my-module-1.0.0.tgz
   ```

3. Run [Are the Types Wrong?](https://arethetypeswrong.github.io) on the tarball, with the `esm-only` profile:

   ```bash [Terminal]
   npx @arethetypeswrong/cli ./my-module-1.0.0.tgz --profile esm-only
   ```

   The profile leaves out `node10` resolution, and `require` under `node16`, which can't load an ES module. A module that sets `types` and `typesVersions` for `node10` consumers checks `node10` too, with `--ignore-rules cjs-resolves-to-esm` in place of `--profile esm-only`. See [The types field](/docs/guide/modules/module-builder/upgrade-v2#the-types-field) in the upgrade guide.

### Releasing a version

A `release` script can publish a new version in one step. Use the package manager that applies your setup:

::code-group

```json [Source exports]
{
  "scripts": {
    "release": "pnpm lint && pnpm test && pnpm prepack && changelogen --release && pnpm publish && git push --follow-tags"
  }
}
```

```json [dist]
{
  "scripts": {
    "release": "npm run lint && npm run test && npm run prepack && changelogen --release && npm publish && git push --follow-tags"
  }
}
```

::

The script runs these steps:

1. Run the linter, the tests, and the build. The release stops if any of them fails.
2. Run `changelogen --release`, which bumps the version, updates `CHANGELOG.md` from your commit messages, and commits and tags the result.
3. Publish the package. `prepack` builds the module again, so `dist` has the new version.
4. Push the release commit and its tag with `git push --follow-tags`.

Commit your changes before you run `release`. `changelogen` reads [Conventional Commits](https://www.conventionalcommits.org) to choose the version bump and to write the changelog.

With source exports, publish with `pnpm publish` or `yarn npm publish`. A `release` script that runs `npm publish` fails, even when `pnpm run` starts it. `npm publish` of a tarball that `pnpm pack` wrote works, because its `package.json` already has the `dist` paths, and the build doesn't run again.

### Checks on published paths

Every build reads the path fields of `package.json`, such as `exports`, `main`, and `types`. It reads them with the fields of `publishConfig` in place of the top-level ones. The build fails before it starts when one of them points at a path that doesn't work once the package is installed:

- A TypeScript source other than a declaration, which Node doesn't load from `node_modules`.
- A path that the pack leaves out, because `files` doesn't list it. Without `files`, a path into `.nuxt` counts as left out.

Every pack includes `package.json` and the file that `main` points at, so `files` doesn't have to list them. To publish a file other than a TypeScript source as it is, list it in `files`:

```json [package.json]
{
  "files": ["dist", ".nuxt/my-module.css"],
  "imports": {
    "#my-module/styles.css": "./.nuxt/my-module.css"
  }
}
```

The build checks an entry of `imports` in the same way once the build is done, and only when the build output imports it. An entry that the build bundles into `module.mjs` can keep pointing at `src`.

### Checks when you pack

When `tsdown` or `nuxt-module-build build` runs as the `prepack` or `prepublishOnly` script, the build also checks how the package manager packs `package.json`. It fails when the package manager would publish a path that points at your sources:

- The package manager has to apply `publishConfig` to each field that points at your sources. pnpm applies it to all of them. Yarn 4 applies it to every field except `typesVersions`. Yarn 3 applies it to `exports`, `imports`, `main`, and `module`, and Yarn 2 to `main` and `module`. npm, Yarn 1, and bun pack `package.json` as written.
- `publishConfig` has to set each of those fields, to paths that pass the [checks on published paths](#checks-on-published-paths).

The build reads the package manager from the `npm_config_user_agent` and `npm_execpath` environment variables. It reads the script name from `npm_lifecycle_event`.

A `prepack` script that runs another script, such as `"prepack": "npm run build"`, isn't checked, because the nested script runs as `build`. Run `tsdown` or `nuxt-module-build build` from `prepack` directly. `prepack` can run other commands after it, such as `"prepack": "tsdown && pnpm build:client"`, and is still checked.

After the build, a warning lists the paths in `package.json` that the build didn't produce.
