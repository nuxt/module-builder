title: Exports
description: Publish more entry points than the module itself, such as utilities, composables, and components.
---

The root export of a module is its definition, `dist/module.mjs`, with `dist/types.d.mts` for its types. The root also re-exports the named values and types that `src/module.ts` exports. Anything else that you want users to import by name needs its own subpath in the `exports` of `package.json`.

The examples on this page show the published `exports`, which point at `dist`. With source exports, put them in `publishConfig.exports`, and point each subpath of `exports` at its source. See [Source exports](#source-exports).

## Bundled entries

A [bundled entry](/docs/guide/modules/module-builder/configuration#bundled-entries), such as `./src/utils` in `builder({ entries })`, builds into `dist/<name>.mjs` and `dist/<name>.d.mts`. Export it with both:

```json [package.json]
{
  "exports": {
    ".": {
      "types": "./dist/types.d.mts",
      "import": "./dist/module.mjs"
    },
    "./utils": {
      "types": "./dist/utils.d.mts",
      "import": "./dist/utils.mjs"
    }
  }
}
```

Users then import it as `my-module/utils`. A bundled entry suits code that runs alongside the module, such as helpers for `nuxt.config` or for other modules:

```ts [nuxt.config.ts]
import { defineMyModuleOptions } from 'my-module/utils'

export default defineNuxtConfig({
  modules: ['my-module'],
  myModule: defineMyModuleOptions({ greeting: 'Hi' }),
})
```

TypeScript reads the `types` condition of each export under the `bundler` and `node16` module resolution, which Nuxt apps use. `node10` module resolution ignores `exports`, and these docs don't cover it. If your module keeps a top-level `types` field or `typesVersions` for it, see [Update the paths in package.json](/docs/guide/modules/module-builder/upgrade-v2#3-update-the-paths-in-packagejson) in the upgrade guide.

## Runtime files

You can export files in `src/runtime/` too, from their output in `dist/runtime/`. An app can then import them explicitly, as well as through whatever the module registers for auto-import.

To export a set of components, re-export them from an `index.ts` in the same directory:

```ts [src/runtime/app/components/index.ts]
export { default as Button } from './Button.vue'
export { default as Card } from './Card.vue'
```

Then point an export at its output:

```json [package.json]
{
  "exports": {
    ".": {
      "types": "./dist/types.d.mts",
      "import": "./dist/module.mjs"
    },
    "./components": {
      "types": "./dist/runtime/app/components/index.d.ts",
      "import": "./dist/runtime/app/components/index.js"
    }
  }
}
```

An app that installs the module can now import each component with its full type:

```vue [app.vue]
<script setup lang="ts">
import { Button } from 'my-module/components'
</script>

<template>
  <Button label="Save" />
</template>
```

To register the same components for auto-import, pass the index to `addComponentExports` from `@nuxt/kit`. Each named export becomes a component, prefixed with `prefix`:

```ts [src/module.ts]
import { addComponentExports, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module', configKey: 'myModule' },
  setup() {
    const resolver = createResolver(import.meta.url)

    addComponentExports({
      filePath: resolver.resolve('./runtime/app/components/index'),
      prefix: 'My',
    })
  },
})
```

`<MyButton>` and `<MyCard>` are then available without an import.

Composables work the same way. Export them from a file in the runtime directory, and point a subpath at its output:

```ts [src/runtime/app/composables/index.ts]
export { useGreeting } from './useGreeting'
```

```json [package.json]
{
  "exports": {
    "./composables": {
      "types": "./dist/runtime/app/composables/index.d.ts",
      "import": "./dist/runtime/app/composables/index.js"
    }
  }
}
```

To register them for auto-import, pass each one to `addImports`, or pass their directory to `addImportsDir`:

```ts [src/module.ts]
import { addImports, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module', configKey: 'myModule' },
  setup() {
    const resolver = createResolver(import.meta.url)

    addImports({
      name: 'useGreeting',
      from: resolver.resolve('./runtime/app/composables/useGreeting'),
    })
  },
})
```

::note
With `exports` that point at `dist`, these subpaths resolve once the module has been built. [Source exports](#source-exports) resolve them to your sources while you develop.
::

## Source exports

With [source exports](/docs/guide/modules/module-builder/develop-and-publish#source-exports), `exports` point at your sources, and `publishConfig.exports` holds the paths in `dist`. The playground, and anything else that installs the module from the workspace, then loads every export from `src/` without a build:

```json [package.json]
{
  "exports": {
    ".": {
      "types": "./.nuxt/module-builder/types.d.mts",
      "import": "./src/module.ts"
    },
    "./utils": "./src/utils.ts",
    "./components": "./src/runtime/app/components/index.ts"
  },
  "publishConfig": {
    "exports": {
      ".": {
        "types": "./dist/types.d.mts",
        "import": "./dist/module.mjs"
      },
      "./utils": {
        "types": "./dist/utils.d.mts",
        "import": "./dist/utils.mjs"
      },
      "./components": {
        "types": "./dist/runtime/app/components/index.d.ts",
        "import": "./dist/runtime/app/components/index.js"
      }
    }
  }
}
```

- Each subpath of `exports` points at the source file that the build turns into the matching path of `publishConfig.exports`.
- `publishConfig.exports` replaces `exports` as a whole, so it repeats every subpath.
- The root export's `types` condition points at the declarations that [`nuxt-module-build prepare`](/docs/guide/modules/module-builder/commands#prepare) writes. The [type augmentations](/docs/guide/modules/module-builder/project-structure#srcmodulets) of `src/module.ts` then apply in the playground.
- A subpath has no augmentations, so it points at its source alone.
- A subpath that code outside Nuxt imports, such as a plugin for a plain Vite app, can keep pointing at `dist` in `exports`. That code then loads the built file. Build the module before you use it.

The build checks the paths in `publishConfig.exports`, not the source paths in `exports`. See [Checks on published paths](/docs/guide/modules/module-builder/develop-and-publish#checks-on-published-paths).

## Importing your own exports

Runtime code and module code can import the module's own package name, such as `my-module/utils`. The build never bundles these imports, so they resolve to the published files in the app that installs the module.

While the build generates declarations, these imports resolve to your sources instead, so they type-check before `dist` exists. With source exports, the build reads the subpaths and their `dist` paths from `publishConfig.exports`.
