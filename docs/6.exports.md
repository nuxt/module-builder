title: Exports
description: Publish more entry points than the module itself, such as utilities, composables, and components.
---

The root export of a module is its definition, `dist/module.mjs`, with `dist/types.d.mts` for its types. Anything else you want users to import by name needs its own subpath in the `exports` of `package.json`.

## Bundled entries

A [bundled entry](/docs/guide/modules/module-builder/configuration#bundled-entries) builds into `dist/<name>.mjs` and `dist/<name>.d.mts`. Export it with both:

```json [package.json]
{
  "exports": {
    ".": {
      "types": "./dist/types.d.mts",
      "import": "./dist/module.mjs"
    },
    "./utils": {
      "types": "./dist/utils.d.mts",
      "import": "./dist/utils.mjs"
    }
  },
  "build": {
    "entries": ["./src/utils"]
  }
}
```

Users then import it as `my-module/utils`. A bundled entry suits code that runs alongside the module, such as helpers for `nuxt.config` or for other modules.

TypeScript reads the `types` condition of each export with the `bundler` and `node16` module resolution, which Nuxt apps use. `node10` module resolution ignores `exports`, and these docs don't cover it. If your module keeps a top-level `types` field or `typesVersions` for it, see [The types field](/docs/guide/modules/module-builder/upgrade-v2#the-types-field) and [typesVersions paths](/docs/guide/modules/module-builder/upgrade-v2#typesversions-paths) in the upgrade guide.

## Runtime files

Files in `src/runtime/` can be exported too, from their output in `dist/runtime/`. This lets an app import them explicitly, as well as through whatever the module registers for auto-import.

To export a set of components, re-export them from an `index.ts` in the same directory:

```ts [src/runtime/components/index.ts]
export { default as Button } from './Button.vue'
export { default as Card } from './Card.vue'
```

Then point an export at its output:

```json [package.json]
{
  "exports": {
    ".": {
      "types": "./dist/types.d.mts",
      "import": "./dist/module.mjs"
    },
    "./components": {
      "types": "./dist/runtime/components/index.d.ts",
      "import": "./dist/runtime/components/index.js"
    }
  }
}
```

An app that installs the module can now import each component with its full type:

```vue [app.vue]
<script setup lang="ts">
import { Button } from 'my-module/components'
</script>

<template>
  <Button label="Save" />
</template>
```

To register the same components for auto-import, pass the index to `addComponentExports` from `@nuxt/kit`. Each named export becomes a component, prefixed with `prefix`:

```ts [src/module.ts]
import { addComponentExports, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module', configKey: 'myModule' },
  setup() {
    const resolver = createResolver(import.meta.url)

    addComponentExports({
      filePath: resolver.resolve('./runtime/components/index'),
      prefix: 'My',
    })
  },
})
```

`<MyButton>` and `<MyCard>` are then available without an import. Composables and utilities work the same way: export them from an index, and register them with `addImports` or `addImportsDir`.

::note
A [stub build](/docs/guide/modules/module-builder/commands#build-stub) doesn't write `dist/runtime/`. These subpaths resolve once the module has been built with `nuxt-module-build build`.
::

## Importing your own exports

Runtime code and module code can import the module's own package name, such as `my-module/utils`. These imports are never bundled, and resolve to the published files in the app that installs the module. While the build generates declarations, they resolve to your sources instead, so they type-check before `dist` exists.
