The builder works with this layout:

```bash
my-module/
├── src/
│   ├── module.ts      # the module definition
│   └── runtime/       # code added to the app that installs the module
│       ├── app/       # components, composables, plugins, and other app code
│       └── server/    # server routes, middleware, and Nitro plugins
├── playground/        # a Nuxt app that installs the module
├── package.json
└── tsconfig.json
```

## `src/module.ts`

The module entry. Its default export is the module definition, created with `defineNuxtModule` from `@nuxt/kit`. The build bundles it into `dist/module.mjs`.

The builder also reads these type exports, and adds them to the types of the app that installs the module:

| Export | Augments | Used for |
|---|---|---|
| `ModuleOptions` | | The module's key in `nuxt.config`. When it isn't exported, it's inferred from the default export. |
| `ModuleHooks` | `NuxtHooks` from `@nuxt/schema` | Build-time hooks the module calls, which apps and other modules register with `hooks` or `nuxt.hook()`. |
| `ModuleRuntimeHooks` | `RuntimeNuxtHooks` from `#app` | Runtime hooks the module calls, which plugins register with `nuxtApp.hook()`. |
| `ModuleRuntimeConfig` | `RuntimeConfig` from `@nuxt/schema` | Private runtime config keys the module adds. |
| `ModulePublicRuntimeConfig` | `PublicRuntimeConfig` from `@nuxt/schema` | Public runtime config keys the module adds. |

```ts [src/module.ts]
import { addPlugin, createResolver, defineNuxtModule } from '@nuxt/kit'

export interface ModuleOptions {
  greeting: string
  apiKey: string
}

export interface ModuleHooks {
  'my-module:init': (options: ModuleOptions) => void
}

export interface ModuleRuntimeHooks {
  'my-module:ready': () => void
}

export interface ModuleRuntimeConfig {
  myModule: { apiKey: string }
}

export interface ModulePublicRuntimeConfig {
  myModule: { greeting: string }
}

export default defineNuxtModule<ModuleOptions>({
  meta: {
    name: 'my-module',
    configKey: 'myModule',
  },
  defaults: {
    greeting: 'Hello',
    apiKey: '',
  },
  setup(options, nuxt) {
    const resolver = createResolver(import.meta.url)

    nuxt.options.runtimeConfig.myModule = { apiKey: options.apiKey }
    nuxt.options.runtimeConfig.public.myModule = { greeting: options.greeting }
    addPlugin(resolver.resolve('./runtime/app/plugins/greeting'))
  },
})
```

Relative imports in `src/module.ts`, and in every file it imports outside the runtime directories, carry the imported file's extension: `./utils.ts`, not `./utils`. The [stub build](/docs/guide/modules/module-builder/commands#build-stub) and [`prepare`](/docs/guide/modules/module-builder/commands#prepare) load these files with Node, which resolves relative specifiers as written. Type-only imports are exempt.

Paths into the runtime directory, such as the one passed to `addPlugin` above, are written without an extension. `src/runtime/app/plugins/greeting.ts` is emitted as `dist/runtime/app/plugins/greeting.js`. Nuxt resolves a path without an extension to the file that exists. That's the `.ts` source in development, and the `.js` output once the module is published.

## `src/runtime/`

Code that the module adds to the app: components, composables, plugins, server routes, stylesheets, and any other files. The module registers them from `setup()`, with utilities such as `addPlugin`, `addComponent`, or `addServerHandler`.

Put code for the app in `src/runtime/app/`, and code for the server in `src/runtime/server/`. In an app that installs the module, Nuxt type-checks `runtime/server/` in the server context and the rest of `runtime/` in the app context. The module's own `tsconfig.json` type-checks all of `src/runtime/` with one configuration. See [Augment Types](/docs/guide/modules/recipes-advanced#augment-types) in the Module Author Guide.

Each file is transpiled on its own into `dist/runtime/`, keeping its name and its imports. See [Build output](/docs/guide/modules/module-builder/output#runtime-files) for how each kind of file is emitted.

Files in the runtime directory can't rely on auto-imports, since Nuxt doesn't apply them to files in `node_modules`. Import what you use from `#imports`, or from the package that provides it:

```ts [src/runtime/app/composables/useGreeting.ts]
import { useRuntimeConfig } from '#imports'

export function useGreeting() {
  return `${useRuntimeConfig().public.myModule.greeting} from my-module`
}
```

The `.nuxt` that [`prepare`](/docs/guide/modules/module-builder/commands#prepare) generates for your module disables auto-imports too. A missing import is then a type error, in your editor and in the build.

To transpile another directory in the same way, add it to [`build.entries`](/docs/guide/modules/module-builder/configuration#directory-entries).

## `playground/`

A Nuxt app that installs your module, to try it out while you develop it. The starter installs the module by its package name:

```json [playground/package.json]
{
  "dependencies": {
    "my-module": "file:.."
  }
}
```

```ts [playground/nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['my-module'],
  myModule: {},
})
```

The playground therefore loads the module through its `package.json` `exports`, from `dist`. A [stub build](/docs/guide/modules/module-builder/commands#build-stub) points `dist` at your sources, so the playground runs them without a full build after every change. See [Develop and Publish](/docs/guide/modules/module-builder/develop-and-publish#working-in-the-playground).

## `package.json`

A minimal `package.json` for a module:

```json [package.json]
{
  "name": "my-module",
  "version": "1.0.0",
  "license": "MIT",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/types.d.mts",
      "import": "./dist/module.mjs"
    }
  },
  "main": "./dist/module.mjs",
  "files": [
    "dist"
  ],
  "scripts": {
    "prepack": "nuxt-module-build build",
    "dev": "nuxt dev playground",
    "dev:prepare": "nuxt-module-build build --stub && nuxt-module-build prepare && nuxt prepare playground"
  },
  "dependencies": {
    "@nuxt/kit": "^4.0.0"
  },
  "devDependencies": {
    "@nuxt/module-builder": "^2.0.0",
    "nuxt": "^4.0.0",
    "tsdown": "^0.23.7",
    "typescript": "^5.9.3 || ^6.0.0"
  }
}
```

- `exports["."].types` points at `dist/types.d.mts`, which re-exports the module's types along with the [augmentations](#srcmodulets) above.
- `dependencies`, `peerDependencies`, and `optionalDependencies` stay external to `dist/module.mjs`. Any other package that the module entry imports, such as a `devDependency`, is bundled into it.

After every build, the builder checks the paths in `exports`, `main`, `module`, `types`, and `typesVersions`, and warns about any that the build didn't produce.

To publish more entry points, such as `my-module/utils` or `my-module/components`, see [Exports](/docs/guide/modules/module-builder/exports).

## `tsconfig.json`

The module's own `tsconfig.json` extends the `.nuxt/tsconfig.json` that `prepare` generates in the module root. See [TypeScript](/docs/guide/modules/module-builder/typescript).
