The builder works with this layout:

```bash
my-module/
├── src/
│   ├── module.ts      # the module definition
│   └── runtime/       # code added to the app that installs the module
│       ├── app/       # components, composables, plugins, and other app code
│       └── server/    # server routes, middleware, and Nitro plugins
├── playground/        # a Nuxt app that installs the module
├── package.json
├── tsconfig.json
└── tsdown.config.ts   # the build configuration
```

## `src/module.ts`

The module entry. Its default export is the module definition, created with `defineNuxtModule` from `@nuxt/kit`. The build bundles it into `dist/module.mjs`.

The builder also reads these type exports, and adds them to the types of the app that installs the module:

| Export | Augments | Used for |
|---|---|---|
| `ModuleOptions` | | The module's key in `nuxt.config`. When it isn't exported, it's inferred from the default export. |
| `ModuleHooks` | `NuxtHooks` from `@nuxt/schema` | Build-time hooks the module calls, which apps and other modules register with `hooks` or `nuxt.hook()`. |
| `ModuleRuntimeHooks` | `RuntimeNuxtHooks` from `#app` | Runtime hooks the module calls, which plugins register with `nuxtApp.hook()`. |
| `ModuleRuntimeConfig` | `RuntimeConfig` from `@nuxt/schema` | Private runtime config keys the module adds. |
| `ModulePublicRuntimeConfig` | `PublicRuntimeConfig` from `@nuxt/schema` | Public runtime config keys the module adds. |

```ts [src/module.ts]
import { addPlugin, createResolver, defineNuxtModule, updateRuntimeConfig } from '@nuxt/kit'

export interface ModuleOptions {
  greeting: string
  apiKey: string
}

export interface ModuleHooks {
  'my-module:init': (options: ModuleOptions) => void
}

export interface ModuleRuntimeHooks {
  'my-module:ready': () => void
}

export interface ModuleRuntimeConfig {
  myModule: { apiKey: string }
}

export interface ModulePublicRuntimeConfig {
  myModule: { greeting: string }
}

export default defineNuxtModule<ModuleOptions>({
  meta: {
    name: 'my-module',
    configKey: 'myModule',
  },
  defaults: {
    greeting: 'Hello',
    apiKey: '',
  },
  setup(options) {
    const resolver = createResolver(import.meta.url)

    updateRuntimeConfig({
      myModule: { apiKey: options.apiKey },
      public: { myModule: { greeting: options.greeting } },
    })
    addPlugin(resolver.resolve('./runtime/app/plugins/greeting'))
  },
})
```

[`prepare`](/docs/guide/modules/module-builder/commands#prepare) and the build load `src/module.ts`, and every file it imports by value, with Node. Relative imports in these files carry the imported file's extension, `./utils.ts` rather than `./utils`, and the files use only syntax that Node's type stripping removes. See [Module code](/docs/guide/modules/module-builder/typescript#module-code) for all the rules.

Paths into the runtime directory, such as the one passed to `addPlugin` above, are written without an extension. `src/runtime/app/plugins/greeting.ts` is emitted as `dist/runtime/app/plugins/greeting.js`. Nuxt resolves a path without an extension to the file that exists. That's the `.ts` source when `package.json` points at your sources, and the `.js` output from `dist`.

## `src/runtime/`

Code that the module adds to the app: components, composables, plugins, server routes, stylesheets, and any other files. The module registers them from `setup()`, with utilities such as `addPlugin`, `addComponent`, or `addServerHandler`.

Put code for the app in `src/runtime/app/`, and code for the server in `src/runtime/server/`. In an app that installs the module, Nuxt type-checks `runtime/server/` in the server context and the rest of `runtime/` in the app context. The module's own `tsconfig.json` type-checks all of `src/runtime/` with one configuration. See [Augment Types](/docs/guide/modules/recipes-advanced#augment-types) in the Module Author Guide.

Each file is transpiled on its own into `dist/runtime/`, keeping its name and its imports. See [Build output](/docs/guide/modules/module-builder/output#runtime-files) for how each kind of file is emitted.

Files in the runtime directory can't rely on auto-imports, since Nuxt doesn't apply them to files in `node_modules`. Import what you use from `#imports`, or from the package that provides it:

```ts [src/runtime/app/composables/useGreeting.ts]
import { useRuntimeConfig } from '#imports'

export function useGreeting() {
  return `${useRuntimeConfig().public.myModule.greeting} from my-module`
}
```

The `.nuxt` that [`prepare`](/docs/guide/modules/module-builder/commands#prepare) generates for your module disables auto-imports too. A missing import is then a type error, in your editor and in the build.

To transpile another directory in the same way, add it to [`builder({ entries })`](/docs/guide/modules/module-builder/configuration#directory-entries).

## `playground/`

A Nuxt app that installs your module, to try it out while you develop it. The playground installs the module by its package name. With pnpm, use the `workspace:` protocol and list `playground` in `pnpm-workspace.yaml`:

```json [playground/package.json]
{
  "dependencies": {
    "my-module": "workspace:*"
  }
}
```

With npm, use `"my-module": "file:.."` and list `playground` in the root `workspaces`.

```ts [playground/nuxt.config.ts]
export default defineNuxtConfig({
  modules: ['my-module'],
  myModule: {},
})
```

The playground therefore loads the module through its `package.json` `exports`. With pnpm or Yarn 4, `exports` point at your sources, and `publishConfig.exports` at `dist` for publishing. With npm, Yarn 3 or earlier, or bun, `exports` point at `dist`, and `tsdown --watch` rebuilds it as you change your sources. See [Develop and Publish](/docs/guide/modules/module-builder/develop-and-publish#preparing-a-checkout).

## `package.json`

A minimal `package.json` for a module published with pnpm or Yarn 4:

```json [package.json]
{
  "name": "my-module",
  "version": "1.0.0",
  "license": "MIT",
  "type": "module",
  "exports": {
    ".": {
      "types": "./.nuxt/module-builder/types.d.mts",
      "import": "./src/module.ts"
    }
  },
  "main": "./src/module.ts",
  "files": [
    "dist"
  ],
  "publishConfig": {
    "exports": {
      ".": {
        "types": "./dist/types.d.mts",
        "import": "./dist/module.mjs"
      }
    },
    "main": "./dist/module.mjs"
  },
  "scripts": {
    "prepack": "tsdown",
    "dev": "nuxt dev playground",
    "dev:prepare": "nuxt-module-build prepare && nuxt prepare playground"
  },
  "dependencies": {
    "@nuxt/kit": "^4.0.0"
  },
  "devDependencies": {
    "@nuxt/module-builder": "^2.0.0",
    "nuxt": "^4.0.0",
    "tsdown": "^0.23.7",
    "typescript": "^5.9.3 || ^6.0.0"
  }
}
```

- `exports` and `main` point at your sources while you develop. `exports["."].types` points at the declarations that [`prepare`](/docs/guide/modules/module-builder/commands#prepare) writes, which re-export `src/module.ts` along with the [augmentations](#srcmodulets) above.
- `publishConfig` holds the fields that pnpm and Yarn 4 publish in their place. Its `types` condition points at `dist/types.d.mts`, the built equivalent. See [Source exports](/docs/guide/modules/module-builder/develop-and-publish#source-exports).
- `dependencies`, `peerDependencies`, and `optionalDependencies` stay external to `dist/module.mjs`. Any other package that the module entry imports, such as a `devDependency`, is bundled into it.

npm, Yarn 3 and earlier, and bun publish some or all of these fields as written. With them, point `exports` and `main` at `dist`, leave out `publishConfig`, and build `dist` in `dev:prepare`:

```json [package.json]
{
  "exports": {
    ".": {
      "types": "./dist/types.d.mts",
      "import": "./dist/module.mjs"
    }
  },
  "main": "./dist/module.mjs",
  "scripts": {
    "dev:prepare": "nuxt-module-build prepare && tsdown && nuxt prepare playground"
  }
}
```

Every build checks the paths that `package.json` publishes, with the fields of `publishConfig` in place of the top-level ones. It fails when one of them points at a TypeScript source or at a file that the pack leaves out, and warns about any that the build didn't produce. See [Checks on published paths](/docs/guide/modules/module-builder/develop-and-publish#checks-on-published-paths).

To publish more entry points, such as `my-module/utils` or `my-module/components`, see [Exports](/docs/guide/modules/module-builder/exports).

## `tsconfig.json`

The module's own `tsconfig.json` extends the `.nuxt/tsconfig.json` that `prepare` generates in the module root. See [TypeScript](/docs/guide/modules/module-builder/typescript).

## `tsdown.config.ts`

The build configuration, which adds the `builder()` plugin to tsdown. `tsdown` reads it to build the module. See [Configuration](/docs/guide/modules/module-builder/configuration).
