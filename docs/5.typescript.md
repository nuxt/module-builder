A module has two TypeScript setups: one for the module itself, and one for its playground. This page covers both, and how the build generates the declarations in `dist` from the first.

## The module's `tsconfig.json`

The module root has a `tsconfig.json` of its own, which extends the `.nuxt/tsconfig.json` that [`nuxt-module-build prepare`](/docs/guide/modules/module-builder/commands#prepare) generates there:

```json [tsconfig.json]
{
  "extends": "./.nuxt/tsconfig.json",
  "exclude": ["dist", "node_modules", "playground"]
}
```

This single tsconfig covers `src/module.ts` and `src/runtime/` alike. Your editor, your type check, and the declarations that `nuxt-module-build build` generates all read it, so they see the same types.

The `.nuxt` in the module root types the module as Nuxt sees it with the module installed alone, at its default options, with auto-imports disabled. It's separate from the playground's `.nuxt`, which reflects the playground's configuration and any other modules it installs.

Exclude `playground` so the playground's files are typed by its own tsconfig. Add any other directory that isn't part of the module, such as `docs`, to `exclude` too.

## The playground's `tsconfig.json`

The playground is a Nuxt app, so its `tsconfig.json` is set up like any other Nuxt app's, against the `.nuxt` that `nuxt prepare playground` generates. The starter uses:

```json [playground/tsconfig.json]
{
  "extends": "./.nuxt/tsconfig.json"
}
```

A playground can also use the project references that Nuxt generates for an app. See [TypeScript](/docs/guide/concepts/typescript) in the Nuxt docs.

To type-check the module and the playground, run the type check once in each:

```json [package.json]
{
  "scripts": {
    "test:types": "vue-tsc --noEmit && cd playground && vue-tsc --noEmit"
  }
}
```

## Monorepos

In a monorepo, give the module its own `tsconfig.json` as shown above. Don't rely on a root tsconfig or on an app's `.nuxt` for it. Move any `compilerOptions` the module relies on into it, such as `"types": ["youtube"]` for a global namespace. They then apply to the module's own type check and to its declarations.

The tsconfig that covers your module might extend or reference another app's `.nuxt/tsconfig.json` instead. In that case, the build generates declarations with the module's `./.nuxt/tsconfig.json` plus that tsconfig's own `compilerOptions`, and prints a note. See [Module tsconfig](/docs/guide/modules/module-builder/upgrade-v2#module-tsconfig) in the upgrade guide.

## Declarations

`nuxt-module-build build` generates declarations from your module's own files, with the module's tsconfig:

- The module entry and every other bundled entry, with TypeScript, or with oxc when `isolatedDeclarations` is set.
- Every script in the runtime directory and other directory entries, with TypeScript.
- Every `.vue` file, with `@vue/language-core`, the same tooling that `vue-tsc` uses.

The declaration program leaves out files under the module's `playground*`, `docs`, `test`, `tests`, `fixtures`, `example`, and `examples` directories. It also leaves out files that the tsconfig includes from outside the module root. Files that your module's sources import are still followed, wherever they are.

If `.nuxt` is out of date, the declarations are too. Run `nuxt-module-build prepare` again after you change what the module adds to the types.

### Errors that fail the build

An error that leaves a declaration missing or wrong fails the build. The most common is an export whose inferred type refers to a package your module can't import by name (TS2742, TS2883, or TS4023). Give each export it lists an explicit type annotation. In this example, the handler's arguments are omitted:

```ts
// before
export const handler = defineCachedHandler(...)

// after
export const handler: ReturnType<typeof defineCachedHandler> = defineCachedHandler(...)
```

Syntax errors, and files for which no declaration can be emitted, fail the build as well. See [Portability errors](/docs/guide/modules/module-builder/upgrade-v2#portability-errors) in the upgrade guide for more examples.

### Type errors reported as warnings

Every other type error, such as a wrong argument type, is reported as a warning. The build prints one warning per directory, with the number of errors and the first three. Run your module's own type check to see them all.

Build-time aliases (`#build/*`, `#internal/*`, and other paths into `.nuxt`) are typed as `any` while declarations are generated. So are they in `dist`: an export whose type is inferred through one of them is declared as `any`. Annotate such an export with a type that refers to it by name. The type then resolves against the `.nuxt` of the app that installs the module. See [Other type errors](/docs/guide/modules/module-builder/upgrade-v2#other-type-errors) in the upgrade guide.

### `isolatedDeclarations`

With `isolatedDeclarations: true` in the module's tsconfig, the module entry's declarations come from oxc. Every export then needs an explicit type, including the module definition:

```ts [src/module.ts]
import { defineNuxtModule } from '@nuxt/kit'
import type { NuxtModule } from '@nuxt/schema'

export interface ModuleOptions {
  apiKey: string
}

const module: NuxtModule<ModuleOptions> = defineNuxtModule<ModuleOptions>({
  meta: { name: 'my-module', configKey: 'myModule' },
  setup() {},
})

export default module
```

Without `isolatedDeclarations`, the build prints a reminder once per run outside CI. Both settings work.

## Recommended compiler options

`erasableSyntaxOnly` makes the type check report syntax that Node's type stripping can't run, such as `enum` and parameter properties. The stub build and `prepare` load such syntax only when `tsdown` is installed:

```json [tsconfig.json]
{
  "extends": "./.nuxt/tsconfig.json",
  "compilerOptions": {
    "erasableSyntaxOnly": true
  },
  "exclude": ["dist", "node_modules", "playground"]
}
```

The generated `.nuxt/tsconfig.json` sets `allowImportingTsExtensions`, so relative imports with a `.ts` extension in module code type-check without further settings.
