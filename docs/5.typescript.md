A module has two TypeScript setups: one for the module itself, and one for its playground. This page covers both. It also describes the rules for module code, and how the build generates the declarations in `dist`.

## The module's `tsconfig.json`

[`nuxt-module-build prepare`](/docs/guide/modules/module-builder/commands#prepare) generates a `.nuxt` in the module root, with one tsconfig for each part of the module: `tsconfig.node.json` for `src/module.ts` and the files next to it, `tsconfig.app.json` for `src/runtime/`, `tsconfig.server.json` for `src/runtime/server/`, and `tsconfig.shared.json` for code that both the app and the server use. The module's own `tsconfig.json` references them, with a `tsconfig.module.json` of yours in place of the one for module code:

```json [tsconfig.json]
{
  "references": [
    { "path": "./tsconfig.module.json" },
    { "path": "./.nuxt/tsconfig.app.json" },
    { "path": "./.nuxt/tsconfig.server.json" },
    { "path": "./.nuxt/tsconfig.shared.json" }
  ],
  "files": [],
  "exclude": ["dist", "node_modules", "playground"]
}
```

```json [tsconfig.module.json]
{
  "extends": "./.nuxt/tsconfig.node.json",
  "compilerOptions": {
    "tsBuildInfoFile": "./.nuxt/tsconfig.module.tsbuildinfo",
    "erasableSyntaxOnly": true
  }
}
```

Type-check the module with `vue-tsc -b --noEmit`. Each part is checked with the types it has in an app that installs the module, and the build generates each file's declarations with the project that includes it, so your editor, your type check, and `dist` see the same types. `nuxt typecheck` in the module root checks it as an app instead, and regenerates `.nuxt` without the changes that `prepare` makes, so use it for the playground only, as `nuxt typecheck playground`.

The `.nuxt` in the module root types the module as Nuxt sees it when the module is installed alone. It uses the module's default options, and disables auto-imports. It's separate from the playground's `.nuxt`, which reflects the playground's configuration and any other modules that it installs.

- `erasableSyntaxOnly` makes the type check report the syntax that Node can't run in [module code](#module-code).
- `tsBuildInfoFile` keeps the build info that `vue-tsc -b` writes in `.nuxt`, next to that of the generated tsconfigs.
- The root's `compilerOptions` leave out `types` that only tests or other tools use, such as `"vitest/globals"`, as `prepare` copies them into every part.
- `exclude` leaves out `playground`, so the playground's own tsconfig types its files. Add any other directory that isn't part of the module, such as `docs`.
- Options in the root's `compilerOptions`, such as `"types": ["youtube"]`, apply to every part. To change the options of one part, reference a tsconfig of your own that extends the generated one in its place, as `tsconfig.module.json` does for module code.

The generated tsconfigs set `allowImportingTsExtensions`, so relative imports with a `.ts` extension type-check without further settings.

The app part includes the tests in `test/nuxt` and `tests/nuxt`, as an app's does, and type-checks them without a test runner's globals. To leave them out, add the directory, `test` or `tests`, to `exclude` and run `nuxt-module-build prepare` again.

A runtime file imports the types of module code through the module's own package name, such as `import type { ModuleOptions } from 'my-module'`. The app, server and shared parts resolve it to declarations that `prepare` writes. A relative import such as `'../../module'` type-checks `src/module.ts` in that part instead, without the module's own augmentations. No part has the types of `vite/client`, as in an app: for imports such as `./worker.ts?worker&url`, add `vite` to `devDependencies` and a `.d.ts` in the module root with `/// <reference types="vite/client" />`.

### The generated tsconfigs

`prepare` adapts the tsconfigs that Nuxt generates to a module:

- The app part covers `src/runtime/` and the module's other runtime directories, rather than the whole module root, less the root's `exclude`.
- The root's `compilerOptions`, with those of the tsconfigs that it extends, are copied into all four parts, apart from path options such as `paths` and `rootDir`. Its `types` are added to those that Nuxt sets.
- The module's `.d.ts` files are added, apart from those in the runtime directories, in the output directory, in the root's `exclude`, and in the `playground*`, `docs`, `test`, `tests`, `fixtures`, `example` and `examples` directories. A `.d.ts` with no top-level `import` or `export`, which only declares globals and ambient modules, goes to all four parts. A module augmentation, with a top-level `import` or `export` and a `declare module` or `declare global`, goes to the app part and to module code. Other `.d.ts` modules apply only to the files that import them.
- Module code gets the app's aliases, declarations and JSX options, for the runtime files that it imports. It also gets `.nuxt/module-builder/types.d.mts`, so the [type augmentations](/docs/guide/modules/module-builder/project-structure#srcmodulets) of `src/module.ts` apply to it.
- In the app, server and shared parts, the module's own package name resolves to the declarations of module code that [`prepare`](/docs/guide/modules/module-builder/commands#prepare) writes, and the subpath of each other bundled entry resolves to that entry's declarations.

### Server code outside `src/runtime/server`

The server part covers `src/runtime/server` only. Server code in another runtime directory, such as Nitro plugins in `src/runtime/nitro`, is in the app part, with the app's types and DOM globals, and its declarations are generated with them. To check it as server code, reference a tsconfig that extends the generated server tsconfig:

```json [tsconfig.nitro.json]
{
  "extends": "./.nuxt/tsconfig.server.json",
  "compilerOptions": {
    "tsBuildInfoFile": "./.nuxt/tsconfig.nitro.tsbuildinfo"
  },
  "include": ["./.nuxt/types/nitro-nuxt.d.ts", "./.nuxt/types/nitro.d.ts", "./src/runtime/nitro"]
}
```

Then add the directory to the root's `exclude`, so that `prepare` leaves it out of the app part, and run `nuxt-module-build prepare` again:

```json [tsconfig.json]
{
  "references": [
    { "path": "./tsconfig.module.json" },
    { "path": "./.nuxt/tsconfig.app.json" },
    { "path": "./.nuxt/tsconfig.server.json" },
    { "path": "./.nuxt/tsconfig.shared.json" },
    { "path": "./tsconfig.nitro.json" }
  ],
  "files": [],
  "exclude": ["dist", "node_modules", "playground", "src/runtime/nitro"]
}
```

Its `include` replaces the one that it extends, so it lists the server's declarations, `.nuxt/types/nitro-nuxt.d.ts` and `.nuxt/types/nitro.d.ts`. The build then generates the directory's declarations with this tsconfig, as it tries the module's own tsconfigs before the generated ones. Moving the files into `src/runtime/server` has the same effect, and changes their paths in `dist/runtime`.

### Tests and config files

Other tests, fixtures, and config files in the module root such as `vitest.config.ts` are in none of the parts. Outside CI, `nuxt-module-build prepare` lists the TypeScript files that no referenced tsconfig includes. Type-check tests and config files with a `tsconfig.test.json` that extends the node part, as they run in Node, and add it to the root's `references`:

```json [tsconfig.test.json]
{
  "extends": "./.nuxt/tsconfig.node.json",
  "compilerOptions": {
    "tsBuildInfoFile": "./.nuxt/tsconfig.test.tsbuildinfo"
  },
  "include": ["./.nuxt/nuxt.d.ts", "./.nuxt/nuxt.node.d.ts", "./test", "./*.config.*"],
  "exclude": ["./test/nuxt", "./test/fixtures"]
}
```

- `include` replaces the one it extends, so it lists the declarations that module code is checked with. With a `tests` directory, write `./tests` and `./tests/nuxt`.
- Tests that import module code or runtime files type-check those files with these options too. Tests that use `@nuxt/test-utils/e2e`, or mount components with `@vue/test-utils`, belong here.
- `exclude` leaves out `test/nuxt`, which the app part checks with the app's types. Tests that import from `#imports` or use `mountSuspended` run in the Nuxt environment, so they go in `test/nuxt`. When the root's `exclude` leaves out `test`, the app part doesn't include `test/nuxt`, so remove `./test/nuxt` from this `exclude`.
- `exclude` also leaves out the fixtures. Files that a test imports from `test/fixtures` are checked all the same.
- A test runner's globals, such as `"types": ["vitest/globals"]`, go in its `compilerOptions`.

The note that `prepare` prints, `NUXT_MB_C0303`, gives the number of files in each directory that no referenced tsconfig includes. It leaves out `src`, declaration files, the output directory, `node_modules`, the `playground*`, `docs`, `example` and `examples` directories, the root's `exclude`, and the `exclude` of each referenced tsconfig of your own.

A fixture that is a Nuxt app relies on the `.nuxt` that Nuxt generates for it, with its auto-imports and the other modules that it installs. Type-check it as an app: give it a `tsconfig.json` like the playground's, and run `nuxt typecheck test/fixtures/basic`. It reads module code as the playground does, so it can report the errors in [With source exports](#with-source-exports).

### Errors from checking each part

Each part is type-checked on its own, with the files that it imports and the types that the part has in an app. These are the errors that this can report, with their fixes:

- **Missing `types` in module code** (TS2304, TS2503, such as `Cannot find namespace 'YT'`). Runtime files that module code imports are type-checked with module code too. The root's `types` apply to module code, but a `types` list in `tsconfig.module.json` replaces them, so repeat them there, such as `"types": ["youtube", "google.maps"]`.
- **An augmentation that only another file brings in** (TS2322, TS2339, TS2353). Module code that relies on a type augmentation that only a test or a config file loads needs it in its own tsconfig. For example, a Vite plugin that returns `test` from its `config` hook needs Vitest's augmentation of the Vite config: add `/// <reference types="vitest/config" />` to that file. Or add `"vitest/config"` to a `types` list in `tsconfig.module.json`, which replaces the root's `types`, so repeat those in it too.
- **`erasableSyntaxOnly` outside the module entry** (TS1294). `erasableSyntaxOnly` in `tsconfig.module.json` also applies to other bundled entries next to `src/module.ts`, such as a `src/vite.ts`, and to every file that module code imports, runtime files included. It applies to the server utilities that `.nuxt` declares for auto-import as well, as `.nuxt/nuxt.d.ts` refers to them. Rewrite the syntax there too. A bundled entry that module code doesn't import can be left out of the `include` of `tsconfig.module.json` instead.
- **App code in the server part** (TS2307 for `#app`, TS2305 and TS2724 for app composables in `#imports`, TS2304 and TS2584 for `window` and `document`, TS2724 for typed routes such as `RouteMapI18n`). A server file that imports an app runtime file or module code gets that file type-checked with the server's types. These have no `#app`, no app composables in `#imports`, no DOM globals, and none of the app's typed routes. Move what both parts use into files that only depend on what both parts have. Code in a server file that runs in a browser, such as a function passed to Playwright's `page.evaluate`, needs `/// <reference lib="dom" />` in that file.
- **A runtime config type declared twice** (TS2322, TS2345, TS2339). Nuxt types a runtime config key from the value that the module sets. When the module also declares the key's type, through `ModulePublicRuntimeConfig` or its own augmentation of `RuntimeConfig` or `PublicRuntimeConfig`, and the two types differ, TypeScript uses the declaration that it reads first, or merges them into a type that lacks properties of either. Make the two types agree, or declare the full type.
- **`default` refers to itself** (TS7022 on the default export, TS7023 on a function in it, such as `moduleDependencies`). The module's own `.nuxt/types/modules.d.ts` types its options key and its entry in `ModuleDependencies` from `typeof import('../../src/module').default`. A `moduleDependencies` function without a return type is inferred from that same export. Give it one: `moduleDependencies(nuxt): ModuleDependencies`, with `ModuleDependencies` from `@nuxt/schema`.
- **An ambient module declared twice** (TS2554, TS2748, or a wrong type for an export). A `.d.ts` in the module and a type template that both declare the same ambient module, such as `declare module '#my-module/bindings'`, both apply to each part, and the two declarations merge. Keep one of them.
- **Errors in code that relies on `.nuxt`'s declarations**. Each part includes `.nuxt/nuxt.d.ts` and the declarations it references, such as the module's runtime config, typed routes and type templates. Code that relies on them is checked against them. Fix what they report.
- **Module code that a runtime file imports by relative path** (TS2339 on `nuxt.options`, TS2307 for `#app`). A runtime file that imports from `src/module.ts` or another file of module code by relative path, such as `import type { ImageProvider } from '../../module'`, brings that file into the type check of its own part. The server and shared parts don't have the module's augmentations, so `nuxt.options.<key>` fails there, and so do the imports that module code makes. Import the type through the module's own package name instead, as `import type { ImageProvider } from 'my-module'`, or from a file that only declares types.
- **Vite's module types not found** (TS2307 for an import such as `./worker.ts?worker&url` or `./styles.css?inline`, TS2882 for `import './styles.css'`). No part has the types of `vite/client`. Add `vite` to the module's `devDependencies`, and a `.d.ts` in the module root, such as `env.d.ts`, with `/// <reference types="vite/client" />`. It applies to every part, as described in [The generated tsconfigs](#the-generated-tsconfigs).
- **Errors in tests under `test/nuxt`** (TS2593 for `describe` and `it`, and other errors in tests). The app part includes `test/nuxt` and `tests/nuxt`, so these tests are checked with the app's types and without a test runner's globals. Import `describe` and `it` from `vitest`. Or add the directory to the root's `exclude`, such as `"exclude": ["dist", "node_modules", "playground", "test"]`, run `nuxt-module-build prepare` again, and type-check the tests as described in [Tests and config files](#tests-and-config-files).
- **Errors in a template that the module generates** (such as TS7006 in a `.ts` template). A template with a `.ts` file name that a runtime file imports, through an alias or `#build`, is type-checked in that file's part, with its options. Type the code that the template generates, such as the parameters of its functions.
- **Excessive stack depth** (TS2321). TypeScript stops comparing two deeply nested types once the comparison is too deep, and which comparisons get that far depends on the types in the program. Give the value an explicit type, so that its inferred type isn't compared.
- **An unused `@ts-expect-error`** (TS2578). The part that checks the file reports no error on the line after the directive. Remove the directive. If another check of the same file still reports the error, such as the playground's check with source exports, use `// @ts-ignore` on that line instead.

### Extending `.nuxt/tsconfig.json`

`prepare` also writes `.nuxt/tsconfig.json`, for a `tsconfig.json` that extends it. It type-checks the whole module root as one program, with the app's types, so it doesn't report the [errors from checking each part](#errors-from-checking-each-part). In it, the module's own package name resolves through `package.json`, rather than to declarations of module code. Set `erasableSyntaxOnly` in its own `compilerOptions`, and type-check it with `vue-tsc --noEmit`:

```json [tsconfig.json]
{
  "extends": "./.nuxt/tsconfig.json",
  "compilerOptions": {
    "erasableSyntaxOnly": true
  },
  "exclude": ["dist", "node_modules", "playground"]
}
```

## Module code

`nuxt-module-build prepare` and the build load your module's build-time code with Node, as it is. Module code means these files:

- `src/module.ts`.
- Every file that `src/module.ts` imports by value, including runtime files.
- `tsdown.config.ts`.

Node strips types and resolves imports as written. Module code therefore follows the rules in the following sections. `prepare`, `tsdown`, and `nuxt-module-build build` stop with a list of every import and every piece of syntax that breaks them. Each entry has its file, line, column, and fix, and an entry in a runtime file also names the module code that imports it. Until the list is empty, `prepare` doesn't generate `.nuxt`.

### Relative imports carry their extension

Write the imported file's extension in every relative import: `./utils.ts`, not `./utils`, `./utils.js`, or `./utils/`:

```ts [src/module.ts]
import { resolveOptions } from './options.ts'
import { registerComponents } from './components/index.ts'
```

Type-only imports don't stop the module from loading, because Node never loads them. Write their extensions too. A type check that resolves imports like Node requires them, such as the playground's check of its `nuxt.config.ts` context when the playground sets `future.compatibilityVersion: 5`.

Relative imports in other [bundled entries](/docs/guide/modules/module-builder/configuration#bundled-entries) carry their extension as well. Runtime files that module code doesn't import by value can leave out the extension, because the build adds it to their output.

### Only syntax that type stripping removes

Node removes type annotations, but not TypeScript syntax that generates code. Module code doesn't use `enum`, `namespace` with values, parameter properties, `<Type>value` assertions, `import x = require()`, `export =`, or decorators. Rewrite an `enum` as an object and a union type, a `<Type>value` assertion with `as`, and a parameter property as a field:

```ts [src/options.ts]
export const Theme = { Light: 'light', Dark: 'dark' } as const
export type Theme = typeof Theme[keyof typeof Theme]

export function resolveSize(options: { size?: unknown }) {
  return options.size as number
}

export class Context {
  name: string
  constructor(name: string) {
    this.name = name
  }
}
```

A `namespace` with values becomes plain exports or an object, `import x = require('y')` becomes `import`, `export =` becomes `export default`, and a decorator becomes a function call.

### No tsconfig `paths` aliases

Node doesn't read tsconfig `paths`. Use a relative import, or an entry in the `imports` field of `package.json`, which Node resolves itself and the build bundles:

```json [package.json]
{
  "imports": {
    "#internal/*": "./src/internal/*.ts"
  }
}
```

```ts [src/module.ts]
import { logger } from '#internal/logger'
```

### No values from components or JSX

Node can't load `.vue`, `.tsx`, or `.jsx` files. Move a value that the module needs into a `.ts` file, and import it from there.

### JSON with an import attribute

Import JSON with an import attribute, and read properties from its default export:

```ts [src/module.ts]
import pkg from '../package.json' with { type: 'json' }

console.log(pkg.version)
```

`module.mjs` then contains only the properties that the module reads. Destructuring the import bundles the whole file.

### No values from `#app`, `#imports`, or `#build`

`#app`, `#imports`, and `#build/*` only exist inside a Nuxt app. Import types from them, and move the code that needs their values into a runtime file that the module adds, such as a plugin:

```ts [src/module.ts]
import { addPlugin, createResolver, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  meta: { name: 'my-module', configKey: 'myModule' },
  setup() {
    const resolver = createResolver(import.meta.url)

    addPlugin(resolver.resolve('./runtime/app/plugins/setup'))
  },
})
```

```ts [src/runtime/app/plugins/setup.ts]
import { defineNuxtPlugin } from '#imports'

export default defineNuxtPlugin((nuxtApp) => {
  nuxtApp.hook('app:mounted', () => {
    console.log('my-module is ready')
  })
})
```

## The playground's `tsconfig.json`

The playground is a Nuxt app, so you set up its `tsconfig.json` like any other Nuxt app's. It uses the `.nuxt` that `nuxt prepare playground` generates:

```json [playground/tsconfig.json]
{
  "extends": "./.nuxt/tsconfig.json"
}
```

To type-check the module and the playground, run the type check once in each:

```json [package.json]
{
  "scripts": {
    "test:types": "vue-tsc -b --noEmit && cd playground && vue-tsc --noEmit"
  }
}
```

A playground can also use the project references that Nuxt generates for an app, in a `tsconfig.json` with `"files": []` and `references`. Type-check it with `vue-tsc -b --noEmit`, because `vue-tsc --noEmit` checks no files in that tsconfig. See [TypeScript](/docs/guide/concepts/typescript) in the Nuxt docs.

### With source exports

With [source exports](/docs/guide/modules/module-builder/develop-and-publish#source-exports), the playground resolves the module to your sources. Its type check then includes `src/module.ts`, the runtime files, and the files that they import types from. It checks them with the playground's compiler options.

The root export's `types` condition points at `.nuxt/module-builder/types.d.mts`, so the playground sees the module's [type augmentations](/docs/guide/modules/module-builder/project-structure#srcmodulets).

The type check can report these errors:

- **`#app`, `#imports`, or `#build/*` not found (TS2307, TS2664) in the `nuxt.config.ts` context.** Module code imports types from a runtime file that uses these aliases. Move those types into a file that doesn't import the aliases, such as `src/runtime/types.ts`.
- **Relative imports without extensions (TS2835, TS2834) in the `nuxt.config.ts` context.** This context resolves imports like Node when the playground sets `future.compatibilityVersion: 5`. Add extensions to type-only relative imports as well.
- **Globals that the module declares in its own `.d.ts` not found (TS2304).** The playground doesn't include that file. Reference it with `/// <reference path="..." />` from the files that use the globals.
- **The module's own aliases not found (TS2307).** Move each alias from the module's tsconfig `paths` into the `imports` of `package.json`, with its `dist` paths in `publishConfig.imports`. TypeScript resolves those from the module's files in any project.
- **A virtual module that the module adds not found (TS2307).** Declare its types with `addTypeTemplate(template, { nuxt: true, node: true })` from `@nuxt/kit`, so both of the playground's contexts include them.
- **Other errors in runtime files.** Fix them, or check the module with the same compiler options as the playground.

## Monorepos

In a monorepo, give the module its own `tsconfig.json` and `tsconfig.module.json`, as shown above. Don't rely on a root tsconfig or on an app's `.nuxt` for it. Without a `tsconfig.json` of its own, `prepare` and the build read the nearest tsconfig above the module, which can extend a `.nuxt` that only another `nuxt prepare` writes. Copy into its `compilerOptions` the entries of the repository root's `types` that the module's `src` relies on, such as `"youtube"` for a global namespace, and leave out those only tests or other packages use, such as `"vitest/globals"`. They then apply to the module's own type check and to its declarations.

The tsconfig that covers your module might extend or reference another app's `.nuxt/tsconfig.json` instead, such as a playground's or a monorepo root's. In that case, the build generates declarations with the module's `./.nuxt/tsconfig.json`, plus that tsconfig's own `compilerOptions`, and prints a note, `NUXT_MB_C0301`. Those include `types` and `paths`, apart from paths into the other app's `.nuxt`.

## Declarations

The build generates declarations from your module's own files, each with the project that includes it:

- The module entry and every other bundled entry, with TypeScript. With `isolatedDeclarations`, it uses oxc instead.
- Every script in the runtime directory and in other directory entries, with TypeScript.
- Every `.vue` file, with `@vue/language-core`, the same tooling that `vue-tsc` uses.

The declaration program leaves out files under the module's `playground*`, `docs`, `test`, `tests`, `fixtures`, `example`, and `examples` directories. It also leaves out files that the tsconfig includes from outside the module root. The build still follows files that your module's sources import, wherever they are.

If `.nuxt` is out of date, the declarations are too. Run `nuxt-module-build prepare` again after you change what the module adds to the types.

Declarations are kept in `node_modules/.cache/transpile-dir` and reused while none of the files they were generated from has changed, so building an unchanged module again does no type work. Remove that directory to generate them all again.

### Errors that fail the build

An error that leaves a declaration missing or wrong fails the build. The most common one is an export whose inferred type refers to a package that your module can't import by name (TS2742, TS2883, or TS4023). Such a package is a dependency of a dependency, or another version of a package that your module depends on. The error can come from a `.ts` or a `.vue` file, and lists each export with its file and line. Give each export an explicit type annotation.

When the value comes from a function that your module imports, annotate it with that function's return type. The annotation then follows whichever version of the package the function comes from. In this partial example, the handler's arguments are left out:

```ts
// before
export const handler = defineCachedHandler(...)

// after
export const handler: ReturnType<typeof defineCachedHandler> = defineCachedHandler(...)
```

Otherwise, import a type from a package that your module depends on directly:

```ts
import type { EventHandler } from 'h3'

export const handler: EventHandler = defineEventHandler(...)
```

Syntax errors, and files for which no declaration can be emitted, fail the build as well.

### Other type errors

The build generates declarations without type checking, so it doesn't report other type errors, such as a wrong argument type. Your module's own type check (`vue-tsc -b --noEmit`) reports them: run it as a script of its own, and as a step of its own in CI.

Build-time aliases, such as `#build/*`, `#internal/*`, a module's own generated alias, and other paths into `.nuxt`, are typed as `any` while declarations are generated. They're `any` in `dist` too, so an export whose type is inferred through one of them is declared as `any`, or as `string | number | symbol` for a key type. Annotate such an export with a type that refers to it by name, such as a component's props type or a type imported from the alias. The type then resolves against the `.nuxt` of the app that installs the module:

```ts [src/runtime/app/composables/useButtonSize.ts]
import type { ComputedRef } from 'vue'
import { computed } from 'vue'
import theme from '#build/ui/button'
import type { ButtonProps } from '../components/Button.vue'

export function useButtonSize(props: ButtonProps): ComputedRef<ButtonProps['size']> {
  return computed(() => props.size ?? theme.defaultVariants.size)
}
```

Without the return type, `dist` declares this function as returning `ComputedRef<any>`.

Routes that your module registers with `addServerHandler` are typed from the module's own `.nuxt`. A composable that returns a `useFetch` or `$fetch` result for one of them is declared with the handler's response type. The response of any other route, such as one that the playground or the app defines, is typed `unknown`. To publish a precise type, type those calls or annotate the export:

```ts [src/runtime/app/composables/useItems.ts]
import type { AsyncData, NuxtError } from 'nuxt/app'
import { useFetch } from '#imports'

interface Item {
  id: string
}

export const useItems = () => useFetch<Item[]>('/api/items')

export const useItemsAnnotated = (): AsyncData<Item[] | undefined, NuxtError | undefined> => useFetch('/api/items')

export const fetchItems = () => $fetch<Item[]>('/api/items')
```

### `isolatedDeclarations`

With `isolatedDeclarations: true` in the tsconfig for module code, the module entry's declarations come from oxc. oxc is faster than TypeScript, but every export then needs an explicit type, including the module definition:

```ts [src/module.ts]
import { defineNuxtModule } from '@nuxt/kit'
import type { NuxtModule } from '@nuxt/schema'

export interface ModuleOptions {
  apiKey: string
}

const module: NuxtModule<ModuleOptions> = defineNuxtModule<ModuleOptions>({
  meta: { name: 'my-module', configKey: 'myModule' },
  defaults: { apiKey: '' },
  setup() {},
})

export default module
```

Without `isolatedDeclarations`, the build prints a reminder once per run outside CI. Both settings work.
