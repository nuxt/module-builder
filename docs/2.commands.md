`@nuxt/module-builder` installs the `nuxt-module-build` command, which has two subcommands: `build` and `prepare`. Name the subcommand every time: `nuxt-module-build` without one runs `build` and prints a warning.

The Nuxt CLI runs the same commands as [`nuxt build-module`](/docs/api/commands/build-module): `nuxt build-module build` is `nuxt-module-build build`.

## `build`

```bash [Terminal]
npx nuxt-module-build build [ROOTDIR] [--cwd=<directory>] [--outDir=<directory>] [--sourcemap] [--stub]
```

Builds the module for publishing. This is the command that the `prepack` script runs:

1. If `.nuxt/tsconfig.json` is missing from the module root, it runs [`prepare`](#prepare) first.
2. It reads the [build configuration](/docs/guide/modules/module-builder/configuration) and checks that every relative import in the module code carries its extension.
3. It empties the output directory.
4. It bundles `src/module.ts`, and any other [bundled entry](/docs/guide/modules/module-builder/configuration#bundled-entries), with tsdown.
5. It transpiles `src/runtime/`, and any other [directory entry](/docs/guide/modules/module-builder/configuration#directory-entries), file by file.
6. It generates the declarations of every entry and runtime file, using the [module's `tsconfig.json`](/docs/guide/modules/module-builder/typescript).
7. It loads the built module to write `dist/module.json`, and writes `dist/types.d.mts`.
8. It checks the paths in `package.json` against the files it produced.

The build fails when a declaration can't be generated correctly. Other type errors are reported as warnings. See [TypeScript](/docs/guide/modules/module-builder/typescript#declarations) for both.

See [Build output](/docs/guide/modules/module-builder/output) for the files the build writes.

### Arguments

| Argument | Description |
|---|---|
| `ROOTDIR="."` | The module root. |

### Options

| Option | Default | Description |
|---|---|---|
| `--cwd=<directory>` | | The module root. Takes precedence over `ROOTDIR`. |
| `--outDir=<directory>` | `dist` | The output directory, relative to the module root. It's emptied before every build, so it must be inside the module. |
| `--sourcemap` | `false` | Emit a source map next to every script. |
| `--stub` | `false` | Write a [stub build](#build-stub) instead. |

## `build --stub`

```bash [Terminal]
npx nuxt-module-build build --stub [ROOTDIR] [--cwd=<directory>] [--outDir=<directory>]
```

Writes `dist` as a set of re-exports of your sources, so that anything which loads the module by its package name runs `src/` directly. Use it while you develop the module, with a playground, an app in the same monorepo, or tests that install the module by name. Changes to `src/` don't need another build.

A stub build writes:

- `dist/module.mjs`, which re-exports `src/module.ts`.
- `dist/module.d.mts`, which re-exports the types of `src/module.ts`.
- The same pair of files for every other [bundled entry](/docs/guide/modules/module-builder/configuration#bundled-entries).
- `dist/module.json` and `dist/types.d.mts`, as the full build does.

It doesn't transpile the runtime directory or generate declarations. `src/module.ts` resolves runtime paths relative to itself, so `src/runtime/` is used as it is. A [subpath export](/docs/guide/modules/module-builder/exports) that points into `dist/runtime` resolves after a full build.

Whatever imports the stub loads the TypeScript sources with its own loader, such as the playground's Nuxt. The builder itself loads `src/module.ts` to write `module.json`, with Node's type stripping. Syntax that Node can't strip (`enum`, `namespace`, parameter properties, JSX, and decorators, among others) is transpiled with oxc, which comes with `tsdown`. Without `tsdown`, the stub build fails and lists each use of such syntax. See [Stub builds](/docs/guide/modules/module-builder/upgrade-v2#stub-builds) in the upgrade guide.

Options that a full build rejects in a [deprecated build config](/docs/guide/modules/module-builder/configuration#buildconfigts) are listed as a warning instead, and the stub build continues.

## `prepare`

```bash [Terminal]
npx nuxt-module-build prepare [ROOTDIR] [--cwd=<directory>]
```

Generates `.nuxt` in the module root. It runs `nuxt prepare` on the module root, as a Nuxt app with your module as its only module and auto-imports disabled. It writes nothing to `dist`.

Your module's `tsconfig.json` extends the `.nuxt/tsconfig.json` it generates. That gives your editor, your type check, and the declarations that `build` generates the same types: `@nuxt/schema`, the `#app`, `#imports`, and `#build` aliases, and anything your module adds, such as its templates and server routes. See [TypeScript](/docs/guide/modules/module-builder/typescript).

`prepare` loads `src/module.ts` in the same way as the stub build, so relative imports in module code need their extensions here too. Until they're in place, `prepare` lists the imports to fix and doesn't generate `.nuxt`.

Run `prepare` again after a change to anything the module registers for types: its options, templates, type declarations, or server routes.

### Arguments

| Argument | Description |
|---|---|
| `ROOTDIR="."` | The module root. |

### Options

| Option | Default | Description |
|---|---|---|
| `--cwd=<directory>` | | The module root. Takes precedence over `ROOTDIR`. |

## Developing a module

The starter's `dev:prepare` script runs all three steps that a fresh checkout needs:

```json [package.json]
{
  "scripts": {
    "dev": "npm run dev:prepare && nuxt dev playground",
    "dev:prepare": "nuxt-module-build build --stub && nuxt-module-build prepare && nuxt prepare playground",
    "prepack": "nuxt-module-build build"
  }
}
```

1. `nuxt-module-build build --stub` points `dist` at your sources.
2. `nuxt-module-build prepare` generates the module's own `.nuxt`, for the module's `tsconfig.json`.
3. `nuxt prepare playground` generates the playground's `.nuxt`. The playground installs the module by its package name, so this step loads the stub from step 1.

Run `dev:prepare` after you install dependencies, and again when the types it generates are out of date. `build` runs `prepare` on its own when `.nuxt` is missing. Keeping `prepare` in `dev:prepare` puts the module's types in place before your editor or type check needs them.
